Every number below is measured from `target/release/Y tests/gemm_f16_swiglu_<N>.ysu --emit-ptx`'s actual output (`ptx_emitter::emit_gemm_swiglu_kernel`, dispatched via the 4-param kernel-level `@tile(M, N, K)` shape - `X, Wgate, Wup: GlobalMemory<F16>, Out: GlobalMemory<F32>`) - computing `Out = SiLU(X @ Wgate) * (X @ Wup)`, the gate/up half of an LLM SwiGLU MLP block (`Linear -> SiLU*Linear -> Linear`). ## Update: `cp.async` multi-stage pipelining added - real improvement at every size, still not a win

The "open questions" list below (from when this kernel was first built) named `cp.async` pipelining as the highest-confidence next lever, by direct analogy with what closed most of the base GEMM's own gap to cuBLAS. It was added this session, at the user's explicit request, as a direct extension of `emit_tensor_core_gemm_kernel`'s own N-stage prefetch/compute-overlap algorithm (see that function's doc comment for the `read_stage`/`write_stage`/`next_tile` derivation) to three smem-resident tile streams (`X`, `W_gate`, `W_up`) instead of two.

**One tile change was needed to make room for it**: `cta_k` dropped from 64 to 32. A third stream means one pipeline stage's real footprint (`stage_a_bytes + 2*stage_b_bytes`) is 1.5x a plain GEMM's at the same tile - at `cta_k=64` that floored the achievable depth to a single stage on this project's dev GPU (`safe_smem_ceiling / per_stage_bytes` = 98304/53248 = 1.84, floors to 1) - no room for real overlap, which would have made adding `cp.async` pointless. Halving `cta_k` to 32 (`per_stage_bytes` = 27648) buys 3 real stages (98304/27648 = 3.55, floors to 3) at the cost of twice the K-loop trip count. Confirmed via the kernel's own PTX comment at every tested size: "3 pipeline stages (requested 4, clamped by k_tiles/smem)". Register pressure re-verified via `ptxas -v` after the change: 122 registers/thread, 0 spills, at all four tested sizes (down slightly from the pre-pipelining 127, since `cta_k` doesn't affect accumulator count, only `k_substeps` - the compile-time-unrolled inner loop inside one `emit_gemm_compute_block` call - which halved from 4 to 2).

**Verified correct before trusting the performance numbers**: `cargo test` (71/71, including a new `test_fused_swiglu_pipelined_dispatch_with_real_hw_profile` - `HardwareProfile::default()` alone zeroes `max_smem_per_sm_bytes`, which would otherwise silently force every other structural test down the single-buffered fallback path and never actually exercise the new pipelined code at all), then a real re-run of `benchmark_y_swiglu_gemm.py` - `torch.allclose` still passes at all four sizes, `max_abs_diff` essentially unchanged from the pre-pipelining numbers (0.007-0.013), confirming the pipelining changed *when* work happens, not *what* gets computed.

**Result: a real, measured improvement at every size, but the kernel is still slower than eager PyTorch everywhere.** Before -> after pipelining: 512 0.19x -> **0.27x**; 1024 stayed inconclusive both times; 2048 0.71x -> **0.77x**; 4096 0.69x -> **0.79x**. Consistent, positive movement at every measurable size (roughly +30-40% relative improvement at 512, +8-10% at 2048/4096) - pipelining was a real, correctly-identified lever, not a wrong guess - but it closes maybe a third of the remaining gap to parity, not all of it. The kernel is now in the same position the base plain GEMM was in after ITS `ldmatrix`/`mma.sync` rewrite: a real, working, measured improvement, still short of the vendor baseline (see `benchmark_y_tensor_core_gemm_results.md`'s own "genuine ~2-4% improvement, not a dramatic one" framing for the base GEMM - this kernel's pipelining win is larger in relative terms but starting from a worse baseline, landing in the same "real but not yet competitive" place).

### Open questions for next session (in priority order)

1. **Doubled `ldmatrix.x4` reload of `X`'s fragments is still unaddressed** (`emit_gemm_compute_block` is called twice per K-substep, once for `W_gate` and once for `W_up`, each independently reloading `X`'s fragments from shared memory) - the other lever named in the original open-questions list, not touched this round. Restructuring so `X`'s fragments load once and get reused for both `mma.sync` streams would cut real, currently-issued instructions.
2. **Whether a deeper or shallower pipeline (`cta_k` other than 32, or a different `requested_stages`) does better** was not swept this session - 3 stages at `cta_k=32` was the first configuration tried and it worked, but it is not established to be the local optimum. `cta_k=16` (potentially 6 stages, smaller per-iteration work) is the most obvious next data point.
3. **Re-run `ncu --set full`** (needs elevated GPU perf-counter permissions this sandboxed session doesn't have - see `benchmark_y_tensor_core_gemm_results.md`'s "ncu access note") to see whether occupancy, the still-doubled A-fragment reload, or something else now dominates the remaining gap - would sharpen whether (1) or (2) above is the better next move rather than guessing.
4. A full 3-matmul MLP pipeline (adding `down_proj = Out @ Wdown`, reusing the existing, already-benchmarked plain-GEMM kernel unchanged) remains out of scope for the same reason as before - keeping this doc's signal about the fusion itself clean.

## Earlier session: new kernel, built from scratch - the pre-existing SwiGLU code was dead, unreachable, and wrong

The prior session's `emit_vectorized_swiglu_fast` and `emit_fused_matmul_rmsnorm_swiglu` (`ptx_emitter.rs`) were flagged "written speculatively - read it skeptically" and never benchmarked. Reading them confirmed that flag was justified, and worse than a simple bug:

1. **Neither function has any caller anywhere in the codebase** - not from `main.rs`, not from any `.ysu`-triggered dispatch path, not from any test. Both are 100% dead code, unreachable from the real Y CLI.
2. `emit_vectorized_swiglu_fast` has a mechanical PTX-syntax bug: the vector register list is built with `"{{{{...}}}}"` in a Rust `format!` string, which escapes to **literal doubled braces** (`{{%f0,...}}`) in the emitted PTX - not valid PTX vector-register syntax, would fail `ptxas` outright.
3. Past that syntax bug, the function's own math is wrong: it loads 4-wide `x`/`y` vectors but computes SiLU/multiply using only element 0 (`%f0`, `%f4`), then **broadcasts that single scalar result into all 4 output slots** (`{%f9,%f9,%f9,%f9}`) - elements 1-3 of both inputs are loaded and silently discarded; 3 of every 4 output elements would be wrong even if the brace bug were fixed.
4. `emit_fused_matmul_rmsnorm_swiglu` has the same broadcast-a-scalar-to-a-vector-store bug, plus a single hardcoded `mma.sync.m16n8k16` regardless of the requested `m`/`n`/`k` (no K-loop, no tiling) - a sketch of what stages a fused kernel would have, not a working one.

Given zero callers and multiple independent correctness bugs, "fix" would have meant a rewrite in all but name. That earlier session did the rewrite: `tile_gemm_swiglu_operands`/`emit_gemm_swiglu_kernel`/`emit_gemm_swiglu_epilogue` in `ptx_emitter.rs`, dispatched from a new 4-param `@tile(M,N,K)` kernel shape (`X, Wgate, Wup: GlobalMemory<F16>, Out: GlobalMemory<F32>` - told apart from the existing Bias+ReLU 4-param shape purely by `Wup` being F16 where `Bias` is F32, both in `ptx_emitter::tile_gemm_swiglu_operands` and the matching `type_checker::verify_tile_gemm_kernel` validation), computing `Out = SiLU(X @ Wgate) * (X @ Wup)` in one launch so neither the gate nor the up projection is ever materialized in DRAM.

**Reused, not reinvented**: the kernel calls the *same* hardware-validated `emit_gemm_compute_block` (`ldmatrix` + `mma.sync.m16n8k16`, see `benchmark_y_tensor_core_gemm_results.md`) and `emit_gemm_tile_load`/grid-swizzle/warp-decomposition machinery the plain and Bias+ReLU GEMM kernels use - twice per K-tile, once against `Wgate`'s shared-memory tile and once against `Wup`'s, both reading the same `X` tile.

**SiLU math validated standalone before wiring in** (same discipline as the ldmatrix/mma.sync rewrite): a single-thread PTX probe kernel (`ex2.approx.f32`/`rcp.approx.f32` - PTX has no non-approx `ex2`) was run on real sm_89 hardware against `torch.nn.functional.silu` over 2000 random `(gate, up)` pairs before being wired into the real epilogue - max absolute error 3.8e-6, max relative error 4.5e-7, negligible next to FP16 tolerance.

**Correctness: real, verified on hardware at all 4 sizes**, both before and after this session's pipelining work (see "Update" above) - `max abs diff` stayed essentially unchanged (0.007-0.013) across the pipelining change, confirming it altered only scheduling, not results.
