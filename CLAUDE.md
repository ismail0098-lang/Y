# CLAUDE.md - Y Compiler & Language Guidelines

## Overview
**Y** is a systems programming language and hardware-aware compiler targeting CPU (x86-64 / AVX-512) and GPU (NVIDIA PTX) targets. It features hardware probing, safety directives, an R1CS zero-knowledge circuit backend, and a dual-accelerator scheduler that fuses RT Core (ray tracing) and Tensor Core (MMA) pipelines.

The codebase consists of:
- **Rust Bootstrap Compiler** (`src/`): Stable reference compiler (`Y`).
- **Self-Hosted Compiler** (`self_hosted/`): Y compiler written in Y (`.ysu`).
- **Python Package & Examples** (`python/`): Python bindings (`y_lang`) for JIT integration.
- **Tests & Workloads** (`tests/`): Test programs (`.ysu`), CUDA benchmarks (`.cu`), and benchmarks (`.py`).

## Build & Test Commands

### Rust Bootstrap Compiler
- **Build**:
  ```bash
  cargo build
  cargo build --release    # Produces target/release/Y
  ```
- **Run Unit & Integration Tests**:
  ```bash
  cargo test               # Run all Rust unit and integration tests
  cargo test -- <filter>   # Run specific test by name (e.g. cargo test ptx_emitter)
  ```

### Running the Y Compiler CLI
- **LLVM Backend (Default)**: `cargo run -- tests/hello.ysu`
- **Host CPU Backend** (prints a Rust/AVX blob, does not compile it): `cargo run -- tests/hello.ysu --emit-cpu`
- **There is no C backend.** `--emit-c` / `--target=c` / `--c` all report that it was removed and exit 1. `src/c_emitter.rs` is an ORPHAN FILE - `mod c_emitter` appears in neither `lib.rs` nor `main.rs`, so it is not even compiled. Do not fix bugs in it; it has no consumer. (`--c` used to be *silently ignored*, so the command this line documented ran the LLVM backend instead.)
- **PTX Emitter Backend**: `cargo run -- tests/test_drift.ysu --emit-ptx` (this line said `--ptx`, which is not a flag; it was *silently ignored* and the command ran the LLVM backend — the same trap as `--c`, and unrecognised options are a hard error now)
- **Paged Decode Attention**: `cargo run -- tests/paged_decode_attention_128_32_8_16.ysu --emit-ptx`
- **Empirical GEMM Autotuning** (`@tile`d kernels, PTX backend):
  ```bash
  Y tests/gemm_f16_4096.ysu --emit-ptx                    # default: use cached measurements, else analytic model
  Y tests/gemm_f16_4096.ysu --emit-ptx --autotune         # measure this shape on the real GPU, then cache it
  Y tests/gemm_f16_4096.ysu --emit-ptx --autotune-force   # re-measure even if cached (after a codegen change)
  Y tests/gemm_f16_4096.ysu --emit-ptx --no-autotune      # analytic model only, cache ignored (reproducible codegen)
  ```
  `Y_AUTOTUNE=off|cached|measure|force` sets the same thing via the environment.
  Measuring a cold shape costs ~4s (~100s at M=N=K=16384) and is cached per
  (M, N, K, precision, GPU) in `.ysu_hw_profile`.
- **Fused Co-Processor Emitter**: `cargo run -- tests/coprocessor_attention.ysu --emit-coprocessor`
- **R1CS Zero-Knowledge Emitter** (requires the `zk` feature):
  ```bash
  cargo build --release --features zk
  ./target/release/Y <circuit>.ysu --target=r1cs   # writes .r1cs, .sym, .r1cs.txt
  ```
  **The ZK backend is NOT in a default build.** Without `--features zk` the
  binary prints `The ZK Circuit Backend is not compiled into this binary` and
  **exits 0** — a silent no-op that reads as a fast successful run. There is no
  `tests/circuits/` directory; sample circuits are in
  `fuzz/corpus/fuzz_parser/{heavy_circuit,dot_product}.ysu`.
- **End-to-end ZK proof** (Groth16 over BN254; arkworks is a dev-dependency used
  as an independent oracle, the shipping binary still links nothing):
  ```bash
  cargo test --features zk --test zk_groth16_end_to_end
  ```
- **ZK compile-speed benchmark vs circom**: `python3 tests/benchmark_zk_vs_circom.py`

## Architecture & Compiler Modules (`src/`)

Compilation pipeline flow: `.ysu` Source → `lexer` → `parser` → `type_checker` → Backend Emitter.

- **Front-End & Analysis**:
  - `lexer.rs`: Tokenizer for keywords, `@`-directives, register tokens, and MMA intrinsics.
  - `parser.rs` & `ast.rs`: Arena-allocated AST and recursive-descent parser.
  - `type_checker.rs`: Type checking, `@safe` block verification, loop invariants, interval arithmetic, and numerical drift evaluation.
  - `linear_tracker.rs`: Ensures async memory tokens are consumed exactly once.

- **Hardware Optimization & Passes**:
  - `sentinel.rs` & `ysu_gpu_probe.rs`: Hardware prober (measures CPU cache latencies, GPU warp/tensor timings; cached in `.ysu_hw_profile`).
  - `autotuner.rs`: CTA tile / warp-split / pipeline-depth selection. Prefers a cached on-device *measurement*; the analytic `score_candidate` model is the fallback when no measurement exists.
  - `empirical_autotune.rs`: Compiles each candidate through the real emitter, JITs it, correctness-checks it against a CPU reference, and times it under clock-ramp + interleaving discipline.
  - `cuda_runtime.rs`: Minimal `dlopen`-ed CUDA Driver API binding (PTX JIT, launch, events) used by the above. Absent driver => `None`, never a link or build failure.
  - `bank_conflict.rs`: Mathematical solver for shared-memory bank conflict swizzling (`Xor128B`, `Xor64B`).
  - `coprocessor_scheduler.rs` & `ir_grapher.rs`: Dependency graph construction and RT Core/Tensor Core timeline overlap scheduler.
  - `quantization_pass.rs`: Injects vectorized `cvt.rn.f16x2.f32` conversion loops for FP32-to-FP16 pipeline staging.

- **Backend Emitters**:
  - `llvm_emitter.rs`: LLVM IR emission (lowered to native binary via `clang`).
  - `ptx_emitter.rs`: NVIDIA PTX codegen (CTA block tiling, `ldmatrix`, `cp.async`, `mma.sync` tensor cores incl. FP8, paged decode attention). **No Hopper TMA or WGMMA support** - what was here never assembled and was removed; see gotcha #8.
  - `rt_core_emitter.rs`: PTX emitter for RT Core ray-tracing instructions with unified SMEM offsets.
  - `zk_emitter.rs`: R1CS circuit emission (BN254 Fr scalar field arithmetic, single-pass SSA linear-combination folding).
  - `cpu_emitter.rs`: host Rust/AVX source emission (`--emit-cpu`), printed for the user to paste - Y never compiles it.
  - `native_emitter.rs`: direct x86-64 + ELF emission (`--emit-native`). **A straight-line integer subset, and it now REFUSES everything outside it.** It handles `let`, `return`, calls (<=6 int params, System V), all 16 integer binary operators and locals-by-name; it has **no branches**, so `if`/`while`/`for`/`=`/`+=`, floats, strings, indexing and field access are refused with a line number. Gated by `tests/native_emitter_codegen.rs`, which RUNS the produced binary. Before that it emitted an ELF for all of the above and computed the wrong answer under a success banner - see the design-rule table.
  - `c_emitter.rs`: **not compiled** - see the backend list above.

## Gotchas & Development Trapdoors

1. **Shared-Memory Bank Conflict Swizzling (`bank_conflict.rs` & `ptx_emitter.rs`)**:
   - `SmemLayout` XOR swizzling (`Xor128B`) is coupled with `ldmatrix` and `cp.async` address generation in `ptx_emitter.rs`. Do not edit `bank_conflict.rs` or swizzle calculations without running full PTX backend tests (`cargo test ptx_emitter`).
2. **Co-Processor Shared Memory Offset Aliasing**:
   - In `--emit-coprocessor` mode, `coprocessor_scheduler.rs` calculates a unified `coprocessor_smem` shared-memory layout. `rt_core_emitter.rs` relies on exact shared memory offset aliasing—misaligning these offsets triggers `CUDA_ERROR_INVALID_PTX` at runtime.
3. **Autotuner Result Cache (also `.ysu_hw_profile`)**:
   - `--autotune` appends `AUTOTUNE_<precision>_<M>x<N>x<K>_<GPU>=cta_m,cta_n,cta_k,warps_m,warps_n,stages` lines to the same file. Deleting the file to force a hardware re-probe therefore also discards tuning measured on the old configuration—which is the intent.
   - The cache CANNOT detect that GEMM codegen itself changed. After editing `emit_tensor_core_gemm_kernel`, re-tune with `--autotune-force` or the compiler will keep emitting a tile chosen for the old kernel.
   - The key is `(M, N, K)`, so the plain and fused Bias+ReLU GEMMs at the same shape share one entry. The probe kernel measures the plain shape; the fused epilogue is a small tail on an identical mainloop.
   - `Y_CTA_OVERRIDE` outranks the cache and persists in whatever `.ptx` files were written while it was set—regenerate them afterwards or later measurements are silently poisoned.
4. **Hardware Profile Cache (`.ysu_hw_profile`)**:
   - Sentinel microbenchmarks run on initial execution and cache measurements in `.ysu_hw_profile`. Delete `.ysu_hw_profile` to force a re-probe if CUDA drivers, GPU hardware, or CPU governor settings change.
5. **Paged Decode Attention Kernel Naming & Launch Contract (`ptx_emitter.rs`)**:
   - Dispatch is by kernel NAME plus the 7-parameter type signature: `paged_decode_attention_<head_dim>_<num_q_heads>_<num_kv_heads>_<page_size>[_<warps>]`. A name or signature that does not match falls through to generic scalar lowering **silently** - check for the `[Y PAGED DECODE ATTENTION]` PTX comment before trusting any output.
   - Launch contract is fixed: grid `(num_q_heads, num_seqs, 1)`, block `(warps*32, 1, 1)`. The host must match it; nothing checks at runtime.
   - `head_dim` must be 64, 128 or 256 (per-lane vector width), `num_q_heads % num_kv_heads == 0`, and `warps <= 32` (1024-thread CTA cap).
   - The optional `<warps>` defaults to 32, tuned for batch-1 consumer decode (3.3x over 8 warps there). Large-batch serving wants 8 - see `ATTN_DEFAULT_NUM_WARPS`'s measured table. Batch size is a runtime value, so the compiler cannot pick this for you.
   - **There is a second, faster shape: `paged_decode_attention_split_<hd>_<nqh>_<nkvh>_<ps>_<splits>[_<warps>]`, NINE parameters and TWO entry points.** It adds `Partial: GlobalMemory<F32>` `[ns, nqh, splits, hd]` and `PartialMeta: GlobalMemory<F32>` `[ns, nqh, splits, 2]` before `MaxPages`, and the emitter also produces `<name>_reduce` (same parameter list, grid `(nqh, ns, 1)`, block `(32,1,1)`) which combines the per-split partial softmax states. **`Out` is not valid until that second launch has run**, and nothing checks it. Main grid is `(num_kv_heads, num_seqs, splits)`, block `(warps*32, 1, 1)` - note `%ctaid.x` is the KV head here and the QUERY head in the single-pass shape.
     - It fixes the two things the single-pass shape lost to FlashInfer on, and **they had to be fixed together**: one CTA now carries every query head sharing a KV head (so K/V is read once, not `gqa_ratio` times), and `%ctaid.z` partitions the sequence (so the CTA count stops being `num_q_heads * batch`). The head merge ALONE would take batch 1 from 32 CTAs to 8 - a regression, not a fix. Measured against FlashInfer: **1.3–3.7x slower -> 0.76–1.06x**, and 1.10–2.54x faster than the single-pass shape at every size measured.
     - `splits` is compile-time and its optimum depends on batch (16 at batch 1, 4 at batch 32 - measured table in `tests/paged_decode_attention_split_128_32_8_16_4_8.ysu`). Shipping only the 16-split kernel costs 0.76 -> 0.72x in the worst case. Same shape of problem as `<warps>`, one level up.
     - The cross-warp merge buffer is reused across the `gqa_ratio` heads with barriers between them, NOT sliced per head: `num_warps*(2+head_dim)*4` is already 16,640 bytes at 32 warps and head_dim 128, and multiplying it by 4 asks for 66,560 against the 48 KB static limit.
     - The per-split state is **unnormalized** (`m`, `l`, and `sum p*V` before the divide) and f32. Dividing by `l` in the main kernel, or storing the partials as f16, both destroy the combine's ability to rescale by the global max.
     - `emit_attention_split_reduce_entry` writes a whole second `.visible .entry` into `pending_module_items`, with its own register numbering (the emitter's counters are saved, zeroed and restored). A kernel emitter that needs a second entry point must do the same - `emit_kernel`'s counters are per-entry and reusing them produces `.reg` declarations too small for the body.
   - **Hoisting the V load above the QK warp reduction is worth 1.04–1.38x**, and was the entire net gain of a revision that also rewrote the cross-warp merge. `exp` plus five dependent `shfl` sat between that load's issue and its use, so its latency was exposed rather than overlapped. The merge rewrite (warp 0 only, instead of all 32 warps computing an answer 31 of them discard) measured **0.83–1.10x in isolation** - a wash, because ptxas's register count went UP (54 -> 64 at 32 warps). Attribute before claiming: the change that sounds like the optimisation was not the one that paid.
6. **Fused SwiGLU Tile Is Register-Constrained, Not Under-Tuned (`emit_gemm_swiglu_kernel`)**:
   - Its two f32 accumulator arrays (gate, up) cost `num_i*num_j*8` registers EACH, so a 128x128 tile over 2x2 warps needs 256 regs/thread - past ptxas's 255 cap. The kernel is therefore pinned to 4x4 warps, the split that measures 52.5 vs 75.8 TFLOPS in the plain GEMM. That penalty cancels the saved X read: the fusion measures **1.00x against Y's own 2-GEMM unfused path**.
   - `Y_SWIGLU_TILE=cta_m,cta_n,cta_k,warps_m,warps_n` re-runs the sweep. A 13-tile sweep already confirmed the 128x128x32 4x4 default is the best available - do not re-tune it without a structural change (e.g. keeping one accumulator array in shared memory). **Regenerate `tests/gemm_f16_swiglu_*.ptx` afterwards**; the override persists on disk exactly like `Y_CTA_OVERRIDE`.
   - General rule this established: epilogue fusions (bias+ReLU, 1.06x vs cuDNN) only remove work and win; mainloop fusions that add accumulator pressure force a worse tile and tend to net zero. Compute the accumulator-register count before building one.
7. **The PTX Integer Datapath (`ptx_emitter.rs`)**:
   - `U32`/`I32`/`U64`/`I64` element types are lowered for real: typed `ld`/`st`, typed *strides* (the address shift was a hardcoded log2(4) at every site), signed-vs-unsigned arithmetic, and `mul_wide_u32` / `u64_lo32` / `u64_hi32` for the 64-bit limb product whose high half is the carry. **Sub-word widths (`U8`/`U16`/`I8`/`I16`) are still refused**, because an element type is also a stride and there is no byte width threaded through the address math — loading a `u8` at a 4-byte stride reads every fourth element and calls it the array.
   - `let x: U64 = ...` now honours its declared type. It used to alias whatever register the initialiser produced, so a widening or a truncation was whatever the right-hand side happened to be.
   - Intrinsics that are f32/f16 by construction (`block_tile_load`, the vectorised loads, the tile-GEMM machinery) **refuse** a non-float buffer rather than loading its bits as floats.
   - **Integer literals are typed by VALUE, not fixed at I32** (`Expr::IntLit`). A modulus limb such as `4026531841` (0xf0000001) is above `i32::MAX`; typed I32 it is negative, and widening it to 64 bits sign-extends to `0xFFFFFFFF_F0000001`. This turned four limbs of the BN254 result into all-ones, on the one operand pair (p-1 squared) whose conditional subtract actually fires. `cvt.s64.s32` on a legal register: nothing rejects it. Pinned by `hi32(0xf0000001 as U64)` in `tests/ptx_integer_ops.ysu`.
   - **`Stmt::Assign` converts to the TARGET's type.** It used to pick the `mov` width off the value's register prefix, so `x = y` with `x: U64` and `y: U32` emitted `mov.u32 %rd7, %r3` — rejected by ptxas here, but for an f32/u32 pair it would have been a silent reinterpretation of the bits.
   - **`tests/bn254_fr_mul.ysu` is the first cryptographic kernel this backend can express**: BN254 Fr Montgomery multiply, CIOS over eight 32-bit limbs, checked against `zk_field.rs` on the device by `tests/zk_gpu_field.rs`. Its accumulator lives in **per-thread global scratch**, because the backend has no local arrays and `let` binds a name to one register — so it measures **17.0 ns/mul, i.e. 1.03x a single CPU core** on a whole RTX 4070 Ti SUPER (`what_the_gpu_field_multiply_costs`, `--ignored`). That is the scratch traffic, not the arithmetic. **Registers are worth 110x here**: `tools/gen_bn254_kernels.py` generates the same CIOS with every limb in a register and the modulus as immediates (unrolled, because a loop over limb indices cannot be expressed without local arrays), and `tests/bn254_fr_mul_fast.ysu` measures **0.160 ns/mul, 6.23 G mul/s** — 48 registers, zero spill, and **89% of the card's peak DRAM bandwidth**, so it is memory-bound rather than compute-bound. Indexable local storage would remove the generator, not speed the kernel up further.
   - **`block_ptr2d_load_v4` / `block_ptr2d_store_v4` and the `U32x4` type** move 16 bytes in one instruction, read back as `.x/.y/.z/.w` (a lane that does not exist is refused, not silently lane 0). They exist because **ptxas will not merge the scalar form**: every `block_ptr2d_load` carries its own bounds predicate and a predicated load is not a merge candidate, so eight limbs cost eight `LDG.E` no matter how contiguous they are. The wide form keeps the predicate and still costs one instruction. `U32x4` lives in `vec_vars` (four registers under one name) because `emit_expr` returns a single register name and a vector is four.
   - **The layout is planar arrays of `uint4`** (`[(j/4)*4N + i*4 + (j%4)]`), chosen by the profiler and the third one tried. Array-of-structs put a warp's threads 32 bytes apart, so one instruction asked for 32 sectors and used four bytes of each; struct-of-arrays coalesced perfectly but still cost eight instructions per element. Planar `uint4` gives two instructions per element, each covering 512 contiguous fully-used bytes across a warp.
   - **NTT (`tests/bn254_ntt_stage.ysu`, `tests/zk_gpu_ntt.rs`)**: one radix-2 Cooley-Tukey butterfly per thread with the multiply, modular add and modular subtract inlined; 80 registers, zero spill. `N = 2^20` in **8.95 ms of device time, 1.17 G butterflies/s, 60.6x one CPU core**. **The oracle is a naive O(N^2) DFT, and it has to be** — a mutation that drops the twiddle multiply entirely still passes an `INTT(NTT(a)) == a` round trip, because the error cancels between the two directions. Checking a fast transform against a fast transform shares the bug. The first end-to-end figure measured was 2.1x and was **96% harness**: `to_limbs()` is itself a Montgomery multiply, so marshalling 2^20 elements costs about as much as the transform. Report device time and host marshalling separately or the number means nothing. **NCU then took it from 1.81 ms to 0.75 ms at 2^20 (20.8x -> 49.3x a 16-core CPU)**, in two steps that the wall clock alone could never have separated: the layout work above, and the vector intrinsics. `LDG.E` 16 -> 6 `LDG.E.128`, registers 82 -> 56, occupancy 26.9% -> 87.8%, and the dominant stall moved from the local/global instruction queue being full to an ordinary scoreboard wait on memory data. **At 2^23 none of it helps** (23.4 -> 22.4 ms): that size is at 82% of DRAM peak, where a layout moves no fewer bytes. Only FEWER PASSES help there - which is what `tests/bn254_ntt4_stage.ysu` does.
   - **Radix-4 is the answer to being DRAM-bound, and it needs no compiler work.** One 4-point butterfly per thread halves the passes (11 instead of 22 at N=2^22). Measured **1.95x over radix-2 at N=2^22 (10.17 -> 5.21 ms, 12.8x -> 25.0x a 16-core CPU)**, at 84% of DRAM peak, so it is still bandwidth-bound and the next halving is the shared-memory stage fusion below. **The arithmetic saving this bullet used to claim is not real**: it counted "three twiddle multiplies per four points against radix-2's four" and forgot `t3 = (B - D) * i`, which is a full CIOS multiply by the primitive 4th root. Radix-4 costs FOUR multiplies per four points per stage and two radix-2 stages cost four as well - they are equal, and the entire win is the halved pass count. 96 registers, zero spill. **Requires log2(N) EVEN** (N = 4^k) and base-4 digit-reversed input; an odd log2(N) needs a mixed-radix permutation, and the host refuses rather than guessing - a wrong permutation still round-trips, so `INTT(NTT(a)) == a` would not catch it. Checked against the naive DFT *and* element-for-element against the radix-2 path.
   - **Shared-memory stage fusion (`tests/bn254_ntt4_fused.ysu`) is the answer to being DRAM-bound once radix-4 has run out, and it DID need compiler work.** A CTA owns 1024 contiguous elements (32 KB), stages them into shared memory once, runs the five stages whose quarter-stride divides that span (`q = 1, 4, 16, 64, 256`), and writes back once - 11 passes to 7 at N=2^22. 87 registers, zero spill. Measured **5.20 -> 4.00 ms at 2^22 (1.30x)** and 0.66 -> 0.60 at 2^20, by `what_stage_fusion_buys` (`--ignored`).
     - **The pass ratio predicted 1.57x and it did not arrive, because the fused kernel is no longer DRAM-bound.** NCU: DRAM **39%** of peak, SM throughput **71%**, bank conflicts 0.95% of shared wavefronts. It moves one pass of traffic in 1.06 ms where bandwidth alone says 0.45. Removing the memory bound exposed the arithmetic that had been hiding behind it; the fusion did exactly what it claimed to the traffic.
     - **Carry-flag intrinsics exist now (`add.cc`/`addc.cc`/`mad.lo.cc`/`madc.hi.cc`, `carry_op` in `ptx_emitter.rs`, gated by `tests/ptx_carry_chain.rs`), and they were PREDICTED at 2x and MEASURED at 1.06x.** `CARRY` in `gen_bn254_kernels.py` switches the whole BN254 family between the two formulations, so this is the same kernel measured both ways: NTT 2^22 2.63 -> 2.47 ms, MSM kernel-only 279.6 -> 273.8 ms.
       - **The prediction came from reading "the multiplies are only 18% of the SASS, so the other 82% is waste".** The flaw is that the 18% was counted in `IMAD.WIDE.U32`, which produces BOTH halves of a 32x32 product in one instruction. The two-pass carry form cannot: it needs a separate `IMAD` for the low half and an `IMAD.HI` for the high one. So the multiply count DOUBLES (2,400 -> 4,508) exactly as the bookkeeping collapses (moves 2,638 -> 274, `LOP3` 1,308 -> 484, `IMAD.X` 1,710 -> 274), and the totals nearly cancel: 11,728 -> 11,184 instructions, 4.6%. **Count the work an instruction does, not the instructions.**
       - Kept anyway, because 1.06x is real and it is not all it buys: generated `.ysu` shrinks by a third (fused NTT 12,412 -> 8,122 lines), ptxas gets faster, registers fall (`bn254_fr_mul_fast` 48 -> 36, fused NTT 87 -> 83), and unlike the fusions it applies to every field kernel in the repo.
       - **`subc_u32(0, 0)` is `0 - 0 - borrow`, i.e. 0 or 0xFFFFFFFF - the conditional-subtract mask falls straight out of the borrow chain.** That was confirmed on the device with a four-case probe before anything was built on it, not assumed from the ISA doc.
       - **These are the only instructions in this backend that communicate through state appearing in no operand.** A chain must be emitted with nothing between its links that writes CC; `mov` and loads do not, another `.cc` does. The one pass that moves statements (barrier hoisting) stops at the first statement it cannot hoist and a call is one, so it cannot break a chain - but that is a property to preserve deliberately, not an accident.
     - **`w^0 = 1`, so three of stage 0's four CIOS multiplies were computing `x * R * R^-1`.** Dropping them is exact and worth 1.18 -> 1.06 ms, 108 -> 87 registers. **The same saving in the unfused kernel buys nothing** - it is DRAM-bound at 91%. An arithmetic optimisation became worth doing because the bottleneck moved; re-rank the list after every structural change.
     - **The STRIDED fusion (`bn254_ntt4_fused_high{h}.ysu`) finishes the job: 11 passes to 3, 5.20 -> 2.47 ms at 2^22 (2.11x, with carry chains) and 0.61 -> 0.56 at 2^20, which puts Y AHEAD of icicle (2.834 / 0.608 ms) at BOTH sizes.** A CTA takes the same 1024 elements as `4^h` *j*-values across `U = 1024/4^h` consecutive *base* values - `sb*Q0*4^h + p0 + u + j*Q0` - and in *j*-space a stage of quarter `Q0*4^t` is an ordinary radix-4 butterfly of quarter `4^t`. Twiddle index is `p0 + u + Q0*jpos`. The `u` are what keeps it coalesced: `U` consecutive threads share a `j` and so read `U` CONSECUTIVE elements, where without them a warp would ask for 32 separate 16-byte pieces 16 KB apart and use half of every sector.
       - **Depths 2, 3 and 4 are generated, and that is what takes 11 passes to 3 rather than to 4**, because `log4(N) - FUSED_LOG` is not a multiple of 4 and a single depth always leaves a remainder running one launch per stage. Depth 1 is deliberately NOT generated - fusing one stage is the unfused kernel plus a shared-memory round trip, i.e. strictly worse.
       - **`Q0` is a RUNTIME parameter for testability, not generality.** At its production `Q0 = 1024` a depth-4 group needs `N >= 4^9`, and a naive DFT at 2^18 is ~7e10 field multiplies. Passed in, the identical kernel runs at N = 4096 where the oracle costs 16.7M. **`Q0 = 4` is only legal at depth 4**: a depth-`h` CTA needs `Q0 >= 1024/4^h` or `p0 = pg*U` enumerates nothing - the first version of that test was rejected by `cuLaunchKernel` rather than passing quietly. Use `Q0 = 4^(5-h)`.
       - **Mutation-verified, and the split between the three tests is real**: a depth-3 bug is caught ONLY by `every_strided_depth_matches_a_naive_dft`, because no size in the schedule tests uses depth 3. A depth-2 bug is caught by that and by `every_fusion_agrees_with_the_unfused_path` (2^22's schedule is low+4+2). Neutering the swizzle passes everything, correctly - it is a bijection applied on both store and load, so it is a PERFORMANCE property whose guard is the bank-conflict measurement, not a test.
       - **Where it leaves the bottleneck**, profiled at 2^22 before the carry work: `fused` 1.05 ms (DRAM 39%, SM 71%), `fused_high4` 1.03 ms (41%, 68%), `fused_high2` 0.65 ms (**DRAM 92%**, SM 55%). The two deep kernels being SM-bound is what made carry-flag intrinsics look like the top lever; they measured 1.06x (see below). **The remaining lever is the depth-2 kernel, and it is DRAM-bound because a third of what it moves is twiddles, not data** (125.8 MB against 268.4). A stage of quarter `q` carries `3q` twiddle words, so `q = N/4` alone is three quarters of the array - generating them from a two-level table (`w^i = w^(i_hi*2^k) * w^(i_lo)`, two extra multiplies) instead of reading them is worth ~0.65 -> 0.45 ms.
     - The shared-memory slot is XOR-swizzled (`slot ^ ((slot >> 2) & 7)`, `gen_bn254_kernels.py::swizzle`). Without it stage 0 is a 4-way bank conflict: at `q = 1` a thread owns elements `4*tid..4*tid+3`, so its 16-byte slot mod 8 is `{0, 4}` for the whole 8-thread access group. It is a bijection because bits 3 and up pass through unchanged, which is what makes applying it on store and load safe.
     - **One barrier per stage, not two.** At every fused stage a thread's four slots are exactly the four it overwrites, and those quadruples partition the CTA's 1024 slots - so no thread reads a slot another is writing WITHIN a stage. Only stage `t`'s writes against stage `t+1`'s reads need ordering.
   - **Occupancy is a red herring here, and NCU points the wrong way.** It flags 26.9% occupancy / 2 blocks per SM as register-limited, which reads as the obvious fix. Forcing registers down - with **zero spills at every level tested** - is strictly slower: `.maxnreg` 255 -> 0.87 ms, 96 -> 0.86, 80 -> 1.38, 64 -> 1.26, 48 -> 3.39. The kernel is bandwidth-bound with ample ILP. (The occupancy that eventually did arrive came free, from the vector intrinsics needing fewer registers - not from constraining them.) Note also that **`-maxrregcount` on the ptxas command line is silently overridden** by the `.maxnreg` the emitter writes into the PTX, and that number derives from the emitter's VIRTUAL register count, which in a fully unrolled kernel is thousands and buckets straight to 255.

8. **PTX Tests Must Assemble, Not Just String-Match**:
   - `tests_paged_decode_attention::emitted_ptx_actually_assembles` runs real `ptxas -arch=sm_89` over the emitted PTX (skipped when `ptxas` is absent). Adding this immediately caught a `.maxnreg 0` bug that made **every** kernel compiled without a probed `.ysu_hw_profile` structurally invalid. String-matching tests cannot catch illegal instructions - this is also how a `wgmma...s4` that exists on no hardware shipped. Prefer extending this gate to new emitters over adding another substring assertion.
   - **The Hopper TMA / WGMMA surface was entirely non-functional and has been deleted.** Extending the gate to the *intrinsic* surface (`tests/ptx_intrinsics_assemble.rs`, which compiles a probe `.ysu` per intrinsic through the real binary and runs `ptxas`) found that **16 of 19** `emit_*` methods in that family produced PTX the assembler rejects **at their own target arch**, not merely at the wrong one: all four WGMMA GEMM variants, TMA descriptor/bulk/multicast loads, the 3-stage mbarrier pipeline, the warp-specialized producer/consumer pipeline, 2:4 sparse MMA, LOP3 int4 dequant, FP8 scaling MMA, `.maxnreg` emitted mid-body, and a `{{{{` format typo. Every one was dead - reachable from no backend path - and covered only by substring tests, one of which pinned the nonexistent `wgmma...s4.s4` as a regression guard. They are gone rather than fixed: a working TMA path needs host-built `cuTensorMapEncodeTiled` descriptors plumbed in as `.grid_constant` params, mbarrier completion and shared-memory matrix descriptors - a feature to design, not a typo to correct. **Do not re-add any of it without a `ptxas` gate and hardware to run it on.** The reachable `mma.sync` path (`emit_fp8_gemm_kernel`, `emit_tensor_core_gemm_kernel`) was never affected.
   - **Two live, user-callable intrinsics were emitting garbage under a success message.** `tma_load(A, B)` and `wgmma_async()` compiled clean, printed "PTX Assembly generated successfully!", exited 0, and wrote a file `ptxas` rejects with five distinct errors (wrong operand shape, `%f1`..`%f3` outside the declared `.reg .f32 %f<1>` pool, and Hopper instructions under the `.target sm_89` the hardware profile selected). Both now refuse via `unsupported_intrinsic`, which pushes to `PtxEmitter::emit_errors` (renamed from `drift_errors`, since it is no longer only about `@ZeroDrift`) and `main` fails the build. **Refusing is the fix, not a stopgap** - a named gap costs a user five minutes, a plausible-looking broken kernel costs them however long it takes to suspect the compiler.
   - **`pipe.wait(token)` emitted nothing at all.** The bare `pipe.wait` form parses as `Expr::MemberAccess` and was handled; `pipe.wait(t)` parses as an `Expr::Call` whose callee is a `MemberAccess`, and the `Call` arm matched only `Ident` and `Path` callees before `_ => "".into()`. Since `linear_tracker` *requires* the token be passed to something, **the only spelling that compiles was the one that silently did nothing** - the front end proved the copy was awaited exactly once and the backend dropped the await, leaving a race that reads as intermittently wrong output rather than as a compiler bug. Also `cp_async` never emitted `cp.async.commit_group`, so even a present `wait_group 0` was a no-op (it waits on the committed set, which was empty), and its byte count was hardcoded to 16 with the third argument discarded - `cp_async(dst, src, 4)` overran by 12 bytes. Guarded by `async_copy_is_committed_and_awaited` and `cp_async_honours_its_byte_count_and_rejects_illegal_ones`; assembling alone cannot catch a *missing* instruction, so those assert on presence and order.
   - **`barrier_sync()` emitted nothing at all either, and a live pass was optimising around it.** Same shape as `pipe.wait(t)` one row up, and worse in one respect: `emit_block`'s barrier-hoisting pass *recognised* `barrier_sync()` and moved arithmetic across it, so the compiler was reordering around a barrier that did not exist. It went unnoticed because user shared memory was equally unusable - `SharedMemory::alloc` emitted a hardcoded `.shared .align 128 .b8 smem[8192]` with the type argument ignored and no way to index it, so no reachable kernel had a barrier to get wrong.
     - The real surface is `shared_alloc_u32(n)` (module-scope `.shared` array, `n` a positive integer literal, 48 KB static cap - both refused with a reason rather than deferred to a ptxas message about the module), `shared_load_v4` / `shared_store_v4` indexing it in **16-byte units** to match the global `v4` intrinsics, and `barrier_sync()`. `tests/ptx_shared_memory.rs` assembles it AND runs a cross-thread exchange on the device.
     - **The device test does not prove the barrier is present, and that was checked rather than assumed**: with `bar.sync` mutated away the on-device exchange still passes every run, because the eight warps happen to issue their stores before any reaches its load. The string and ordering assertions are what fail under that mutation. A race that does not fire is not a test.
     - **The hoisting pass was unsound, and making the barrier real is what exposed it.** It scanned forward for `Let`/`Assign` with a `BinaryOp` value and, on finding anything else, **kept going** (`j += 1`) instead of stopping - so it reached arbitrarily far ahead and pulled a Montgomery multiply out from under the shared loads defining its operands, emitting `mov.u32 %r, qb0` for an undefined `qb0`. It also checked no dependencies at all: hoisting `x = a + b` above a barrier is legal only if `a` and `b` are available *before* it, and in a shared-memory kernel the values after the barrier are precisely what other threads wrote. It now hoists a contiguous run whose every operand is already bound, using an exhaustive `collect_idents` with no `_ =>` arm.
     - The `.shared` symbol counter (`shared_sym_count`) is monotonic across the module, NOT `shared_arrays.len()` - that vector is drained per kernel, so numbering from its length gives two kernels in one module the same `__y_smem_0`, which only ever appears in a module with two shared-memory kernels in it.
   - **MSM, step one: `tests/bn254_g1_add.ysu` + `tests/zk_gpu_msm.rs`.** BN254 G1 point addition in Jacobian coordinates (`add-2007-bl`, 11 muls + 5 squarings), over the **BASE field Fq** — a different 254-bit prime from Fr and not interchangeable with it: a witness lives in Fr, a point's coordinates live in Fq. `tools/gen_bn254_kernels.py::use_field` switches the modulus so one CIOS implementation serves both. 130 registers, **zero spill**, which only holds because the statement order is chosen for LIVENESS — `Z3` is computed early so `Z1`, `Z2`, `Z1Z1`, `Z2Z2` die before the second half; the readable order needs 11 simultaneous 8-limb temporaries and spills hard.
     - **The oracle is arkworks, compared by point EQUIVALENCE, not by limbs.** Jacobian coordinates are not unique — `(X, Y, Z)` and `(l^2 X, l^3 Y, lZ)` are the same point — and arkworks does not use `add-2007-bl`, so a limb comparison would fail on correct output *and* could pass on wrong output matching another representative. Each result is also asserted on-curve, which is what catches a formula that is self-consistently wrong.
     - `add-2007-bl` is **not complete**: it assumes both inputs non-zero and `P != +-Q`. That is the precondition Pippenger's bucket accumulation is arranged to satisfy, and the test only feeds it independent random points. Doubling therefore needs its own kernel (`bn254_g1_dbl.ysu`, `dbl-2009-l`); `the_add_formula_really_is_incomplete` pins that `add(P, P)` degenerates to `Z = 0` rather than quietly returning something wrong.
     - **Generated temporaries must not collide with type keywords.** A temporary named `U1` produces `U16` at limb 6, and `U8`/`U16`/`U32`/`U64`/`I8` are reserved, so the parser rejects it as a `let` name 9,000 lines into a generated file. `check_names` asserts this at generation time.
   - **MSM, complete: `tests/bn254_msm_bucket.ysu` + `gpu_msm_matches_arkworks`.** Pippenger with the O(n) bucket accumulation on the GPU, one thread per bucket. The host bins point indices by scalar window digit into a CSR pair (`Off[b]..Off[b+1]` names a contiguous slice of `Idx`), which turns the scatter that makes bucket accumulation awkward on a GPU into a gather with **no atomics and no synchronisation at all**. 152 registers, zero spill. `Idx` carries its own length `NIdx`, separate from `NPts`: they are equal only for one window, and sharing the parameter capped a launch at `2^c` threads.
     - **The bottleneck is the single most-loaded bucket, and the top window creates it.** With every window `c` bits wide there are `ceil(254/c)` of them and the top one holds the remainder — at `c = 9` that is 2 bits, so its three live buckets take a QUARTER of all points each, and one thread runs 262,144 serial point additions at `n = 2^20` while 14,847 others wait. Measured kernel time, `n = 2^20`: c=8 421 ms, **c=9 6,380 ms**, c=10 1,730 ms, c=11 7,015 ms, c=12 6,196 ms, c=13 231 ms. That ranking has nothing to do with total work, which falls monotonically as `c` grows; it tracks `2^(c - top window bits)` to within 10% at every point. **Cutting the windows EVENLY instead** (`254 = nw*q + r` gives `r` windows of `q+1` bits and the rest `q`, so the worst imbalance is 2x not 128x) is a pure host change — the kernel never knew how the buckets were cut — and takes the kernel from 231 ms to 35.8 ms, **6.5x**, with the cliffs gone and the sweep smooth. Geometry is therefore parameterised by the NUMBER of windows, not by a width.
     - **Report the fixed-base cost separately from the cold one, and never instead of it.** In Groth16 the G1 bases are the proving key — fixed for the circuit's lifetime — while the scalars are the witness and change every proof, so Montgomery-staging the bases and pushing them over PCIe is a key-load cost, not a per-proof one. At `n = 2^20` against arkworks on **all 32 cores** (272.8 ms): cold end-to-end 108.6 ms = **2.51x**, fixed bases 80.2 ms = **3.40x**, kernel alone 60.5 ms = **4.51x**. Against one core, 5.49x on the kernel. The host phases had to be threaded to say any of this honestly — a single-threaded counting sort was 110 ms of a 285 ms total, larger than the GPU kernel it was feeding, and comparing that against a 32-core baseline would have been the "one core vs the whole GPU" error in reverse.
     - **The oracle is `ark_ec::VariableBaseMSM`, and the control is what makes it worth anything.** An MSM has a failure mode where a wrong answer is still a perfectly valid curve point — get the window shift wrong and every scalar is still consumed and every bucket still accumulated. So `the_msm_oracle_is_not_vacuous` perturbs one scalar by 1 and asserts the result moves by **exactly that point**, and `every_bucket_lands_on_the_curve` checks all ~15,000 buckets satisfy `y^2 = x^3 + 3` after thousands of chained additions. Verified by mutation: neutering the accumulator update fails both MSM tests, and shifting the window combination by one bit fails the main one while leaving the perturbation control green — which is exactly the split those two tests exist to produce.
     - **Parallel binning changes the order points land in a bucket, and that is safe for a stated reason**: curve addition is associative and commutative, so a bucket's sum is the same POINT whatever order it accumulated in. The Jacobian representative differs; the point does not. Do not extend this reasoning to anything that compares limbs.
     - Empty buckets produce garbage by construction — the kernel seeds its accumulator with the slice's first point because `add-2007-bl` has no zero element — and the host substitutes the identity for them, which it can because it built the offsets. The loop is pre-guarded (`setp.ge` + branch, not a do-while), so an empty slice runs zero times.
     - **NCU says the bucket kernel is LATENCY-bound, and the block size was the fix.** DRAM 0.8-8.7%, SM throughput 24-27%, occupancy 11-14%, and **70% of stalls are `wait`** (a dependent ALU result) against 0.05-0.15 on memory. At 136 registers a 256-thread CTA needs 34,816 of an SM's 65,536 - one block per SM. The kernel takes its block size from `block_dim_x()` now and the host picks it (`msm::bucket_block()`, default **128**, `Y_MSM_BLOCK` / `set_bucket_block` to override). End to end: kernel **4.47x -> 6.10x** a 32-core CPU at n=2^22, cold 2.18x -> 2.57x.
       - **The win depends entirely on the window geometry, and measuring one geometry misses it.** Swept at 2^20 (`what_the_msm_block_size_costs`), 256 -> 128: nw=20 1.43x, nw=22 1.53x, nw=25 1.28x, nw=28 1.03x, nw=31 1.05x. Below ~450 threads per SM the kernel is **thread-starved** (not enough buckets to fill the machine) and no block size helps; above it it is **register-limited**. The first version of that benchmark measured only nw=28 and reported a flat 1.00x while the end-to-end run showed 1.18x.
     - **The next lever was BINNING, not the bucket reduction, and the old claim here was wrong.** At nw=20 `reduce` is 5.5 ms - it stops nothing. The phase that grows with the bucket count is `bin`, the largest single phase at every geometry. `where_binning_spends_its_time` (`--ignored`) splits it three ways and settles what inside it costs: at 2^20/nw=20, histogram 3.8 ms, **prefix 23.6**, **scatter 39.3**.
       - **The cursor table IS real** (prefix 0.3 ms at nw=31 -> 23.6 at nw=20) but it is not the biggest piece. It was one SERIAL loop of `nchunk * nb` iterations at stride `nb` - two cache misses each over a 17.8 MB table. Split into a parallel per-bucket total, a serial exclusive prefix only `nb` long, and a parallel cursor fill: **23.6 -> 3.3 ms**. Phase 3 also copied its cursor row out (`cur0.to_vec()`, an `nb`-sized alloc+copy per thread per call) for a row nothing else reads; it mutates `cursor.chunks_mut(nb)` in place now. Binning 67.1 -> 45.9 ms at nw=20, and **the optimum geometry moved from nw=25 to nw=22** as the ranking predicted.
       - **The obvious next fix was tried and LOST, and the reason is worth keeping.** Point-outer scatter writes into every window's slice of `Idx` at once (84 MB at nw=20); window-outer would confine a pass to one window's ~4 MB. Swapping the loops measured **worse** - 22.1 -> 33.1 ms at nw=25 - and went FLAT across geometries. Cause: **false sharing**. A thread's slice of a bucket is `n / (threads * buckets_per_window)` entries, about FOUR u32 at nw=20 - finer than a cache line - and consecutive threads' slices of the same bucket are adjacent in `Idx`. Point-outer lets threads drift across windows independently; window-outer marches all 32 onto the same lines at once. Reverted, with the reasoning in the code so it is not re-attempted.
       - **The scatter's fix was to use FEWER CORES, and two layout attempts lost before that was found.** A radix-partitioned scatter (pass A streams `(bucket, point)` pairs into per-thread partition buffers, pass B gives each partition to one thread so no line is ever shared) measured **0.94x at nw=20 down to 0.38x at nw=31**, and 1.11x at its best partition size over a 2^7..2^15 sweep. It moves 3x the bytes to avoid misses that were mostly not happening: `nb*64` is 8.9 MB at worst and this machine has **64 MB of L3**. Deleted, not kept behind a flag.
         - **The thread sweep is what separated the two explanations, and no other axis could.** Capacity predicts a flat per-entry cost across it (the destination is `nb` lines however many threads walk it); sharing predicts a collapse, because halving the threads doubles a thread's contiguous run inside a bucket. It collapses **17x** (70.7 -> 4.0 ns/entry at nw=20, n=2^22). Scatter ms at 2^22, thr 32/16/12/8/6/4: nw=20 185/132/103/84/**83**/83, nw=22 138/66/**55**/58/68/81, nw=25 69/**48**/52/56/68/80, nw=31 66/**55**/59/64/79/96. **32 threads is never optimal and is 2.2x off at nw=20.** The count is chosen from `nb` alone - the optimum agrees to within one step between n=2^20 and 2^22 - and binning at 2^20 went 41.9 -> 28.5 ms at nw=20, 36.5 -> 24.1 at nw=22, 26.4 -> 19.7 at nw=25.
         - **A host change moved the `kernel only` column and it was NOT a kernel change.** Cold binning is cheaper, so the chosen geometry moved nw=25 -> nw=22, whose kernel is faster; at *matched* geometry the kernel times agree (122.3 vs 118.1 ms at nw=22, 2^22). Check the tuning decision a phase feeds before attributing a change to it. `binning_does_not_depend_on_the_thread_count` pins that the kernel's INPUT is byte-identical at every thread count - true for a stateable reason (a scatter thread owns a contiguous point range and fills each bucket in point order, so every bucket ends in point order however the points are cut), and mutation-verified against two grouping bugs that `every_bucket_lands_on_the_curve` passes straight through.
     - **The scatter's unsafe cross-thread writes are PROVED exactly-once on every run, not argued.** Each thread advances its cursor once per write, so afterwards the cursor holds where that group STOPPED; if every group stopped where the next one STARTED and the last at `off[b+1]`, the runs tile `off[b]..off[b+1]` exactly - every slot written, by one thread, in bounds. Two silent preconditions are asserted with it: the group chunking must tile the input (`zip` TRUNCATES, so a mismatch drops the tail with no panic) and `n*nw` must fit the u32 offsets (a wrap under-allocates `idx` while the cursors run past its end - an out-of-bounds WRITE, not a wrong answer). ~0.2-1.0 ms against a 14-23 ms scatter, and only because the starts array is filled inside the cursor build rather than `clone()`d (the clone was 1.34 ms, nearly all first-touch page faults) and the comparison is group-outer (bucket-outer strides by `nb`: 1.45 ms vs 0.2). Mutation-verified. **The first version of the check was itself wrong** - after the scope EVERY cursor holds an end, so it compared two ends; empty groups exposed it at once. A post-condition wrong in the safe direction proves nothing.
     - Net effect of the block size + binning + scatter work, vs a 32-core CPU, same-session A/B via `Y_MSM_SCATTER_THREADS`, three runs: cold end-to-end **2.49 -> 2.99x** at 2^22 and 2.47 -> 2.93x at 2^20; fixed-base 3.67 -> **4.79x** at 2^22. **At 2^18 it is FLAT (2.51 -> 2.55x)** - one early run read 2.22 -> 2.77x and did not reproduce, and flat is what the phase split predicts there. Sizes at or below 2^16 vary 2x run to run (they sit at the dispatch crossover) - do not read them. The dispatch thresholds in `msm.rs` are now CONSERVATIVE rather than wrong - the GPU wins earlier than they say, and `the_dispatch_thresholds_are_still_true` asserts the shape rather than the crossover, so it still passes. Re-measure with `where_the_gpu_starts_winning` before quoting a number.
     - **`bin` is still the largest host phase** (79-90 ms at 2^22 against `stage` 61 and `h2d` 60) and its scatter is at the floor for this layout. The next real move is binning **on the device**, which also deletes the 84 MB `Idx` upload that `h2d` is mostly made of.
   - **The prover integration: `tests/zk_gpu_groth16.rs`.** Y compiles the circuit, Y solves the witness, and Y's GPU MSM computes four of the five multi-scalar multiplications in a Groth16 proof (`h_query`, `l_query`, `a_query`, `b_g1_query`); `B` in G2 stays on the CPU because `Fq2` arithmetic does not exist in this kernel series yet. The prover is a deliberate transcription of arkworks' `create_proof_with_assignment` rather than a reformulation, so that substituting ONE component is what the test measures.
     - **The acceptance criterion is `Groth16::verify`, plus one thing stronger: the proof is compared ELEMENT FOR ELEMENT against arkworks' own prover run with the same `r` and `s`.** Groth16 is deterministic given its randomness, so `A`, `B`, `C` must match bit for bit. `verify` alone cannot distinguish "the MSMs are right" from "the MSMs are wrong in compensating ways"; this can. Both tests fail under the accumulator mutation, and a tampered public input is rejected.
     - **A proving key is FULL of points at infinity and `add-2007-bl` cannot represent one.** `a_query[i]` is `A_i(tau) * G` and `A_i` is the zero polynomial for every variable absent from the `A` matrix — most of them, in any real circuit. Filtering those pairs out is exact, not an approximation: a term with an identity base contributes nothing whatever its scalar is, and the same holds for a zero scalar (the common case in a sparse witness). Both filters make the MSM legal *and* smaller. The remaining precondition is `P != +-Q` within a bucket, which duplicate points in a query would violate; a violation is caught loudly by the element-wise comparison rather than absorbed.
     - **Measure both sides doing the same work.** The first numbers were 2.80x / 5.94x and were a biased comparison: arkworks' `create_proof_with_reduction` does the R1CS replay and the QAP witness map *inside the call being timed*, and the GPU prover's timer started after both. Correcting that gave 1.24x / 1.35x. Also exclude `cs.is_satisfied()` from the timed path — arkworks only runs it under `debug_assert`, so including it biases the other way.
     - **The phase split, not the ratio, is the deliverable.** It ranked the work and every item it ranked paid off in the order predicted. **Now 2.57x at 262,145 constraints** (970.6 ms CPU vs 377.6 ms), from 1.29x, via two changes:
       - **The R1CS replay was 42% and is deleted, not accelerated.** Y already HAS the constraint matrices; replaying every constraint through `ConstraintSystem::enforce_constraint` to get them back cost 607.9 ms. `create_proof_with_reduction_and_matrices` takes `ConstraintMatrices` directly, so the constraint system never has to exist on the proving path: **607.9 -> 107.8 ms**. Column numbering must be arkworks' exactly (`One` is 0, instance `i` is `i`, witness `j` is `num_instance_variables + j` — `Variable::get_index_unchecked`) because the proving key was generated against it. Rows are sums, so term order within a row is free. **`y_matrices_match_the_arkworks_replay` compares the matrices entry for entry**; "the proof still verifies" is too weak to justify deleting a path.
       - **The QAP figure fell from 239 to 105 ms without anyone touching it**, because `witness_map` calls `to_matrices()` internally and that cost had been attributed to the FFT. Re-attribute after a structural change; a phase's measured cost can include work that has just moved.
       - **The bases are the proving key, so they are staged once** (1,048,580 G1 bases in 37 ms) and only the CSR pair moves per proof. **Only the BASES are filtered for the point at infinity** — filtering zero scalars too would shrink the MSM but make the surviving point set witness-dependent, killing the caching that is worth more; and a zero scalar already costs nothing, since all its window digits are 0 and digit 0 lands in no bucket.
     - **The QAP's seven transforms are on the GPU too (`tests/common/qap.rs`), taking the prover to 3.77x.** Measured before building: the transforms are **89–92% of the witness map** (672 ms of 752 ms at 1M constraints), so the ceiling justified the machinery; the sparse matvecs are the other 10% and are a different problem.
       - **The chain stays on the device.** Seven back-to-back round trips of 2^21 elements is ~900 MB over PCIe and costs more than the transforms save, so `a`, `b`, `c` go up once and `h` comes down once. That needs `bn254_permute` — a table-driven gather — because `bn254_ntt_stage` is decimation-in-time and wants bit-reversed input. The permutation is a **table, not in-kernel bit twiddling**, because it is identical across all seven transforms and also serves radix-4's digit reversal.
       - **Fold every scalar constant into a table and the only other pointwise kernel you need is a subtract.** An iFFT is `(1/n)·DFT` and a coset FFT pre-multiplies by `g^i`, so back to back they are one table `g^i/n`; the closing coset iFFT's `g^-i` absorbs `Z(g)^-1` as well. `bn254_fr_mul_fast` doubles as the scale kernel (`A=Out` is safe — no cross-thread dependency).
       - Checked by **exact equality** against `LibsnarkReduction`, at two sizes so the zero-padding between constraint count and domain size is a real case rather than a corner one. Mutation-verified twice: making the permutation the identity, and turning the modular subtract into an add, both fail it.
     - **Scaling is an S-curve whose shape the QAP work changed.** Before: 4,097 1.27x | 16,385 1.31x | 65,537 1.88x | 262,145 2.59x | 1,048,577 2.56x — *flattening*, because the QAP was O(n log n) on the CPU while the MSM is O(n/log n), so the accelerated share shrank as circuits grew. After: 1.42x | 1.53x | 2.01x | 3.27x | 3.61x — still climbing. The `qap%` column fell 29–37% → 7–10%. **Read the phase split, not the ratio: it predicted this and it is what says the ratio will keep rising.**
     - **The polynomial benchmark circuit cannot measure the PROVER either, and every figure above was taken on it.** The warning recorded for field arithmetic applies one layer up. On a Poseidon chain (~28 terms per row against 1–2) the prover measured **1.66 / 1.80 / 1.76x** where the polynomial circuit said 3.27 / 3.61x, and the phase split inverted: matrix build 73–75% instead of 45%, MSM 10% instead of 39%. The tell was visible earlier and was not read: the polynomial circuit's `b_g1_query` has **one** live base, because its `B` matrix is almost entirely points at infinity — one of the four MSMs was free.
       - Two causes, both invisible at k=2. `y_matrices` combined duplicate terms by scanning the accumulator per term, **O(k²) per row** (sort-and-merge now); and the sparse matvecs were single-threaded, three dot products per row over ~81M terms at 1M constraints.
       - Dense circuit after: **4.28 / 5.65 / 6.17x**. The polynomial circuit gains too (3.61 → ~5.1x at 1M). Both land at **~5–6x** at large sizes; **run-to-run variance is ~15%, so do not quote them more precisely.**
     - **Which circuit you measure decides what to build next, and the two disagree completely.** On the dense circuit the split is matrices 24%, QAP 2%, G1 MSM 27%, **G2 MSM 47%** — the largest phase, needing `Fq2` arithmetic that does not exist in this kernel series. On the sparse one G2 is 8%, because its `B` matrix is nearly empty. A roadmap drawn from the polynomial circuit would rank G2 last.
     - **Do not combine this with the circom compile-time figures.** They measure *emitting* R1CS (154x on `.ysu` input, parity on circom input); circom does not prove at all. Different stage, different baseline — the two do not multiply.
     - **Dispatch: the GPU LOSES below ~57,000 terms cold and ~40,000 staged**, measured by `where_the_gpu_starts_winning`. The choice is per QUERY, not per proof — a Groth16 proof does four MSMs of different sizes, and on this circuit shape `b_g1_query` has **one** live base because the B matrix is nearly all points at infinity. Two traps: (a) `the_dispatch_thresholds_are_still_true` asserts the *shape* of the inequality (CPU wins well below, GPU well above) rather than the exact crossover, so it survives new hardware but catches a stale threshold — it failed on first run because it timed the CPU with only the chunked baseline, which at n=14,000 splits into 32 Pippengers of 437 points; use `cpu_msm_best`. (b) **Dispatch silently disarmed the correctness tests** — at 4,096 constraints everything routed to the CPU and the GPU tests would have kept passing with the kernel deleted. They pass `force_gpu` and assert they got it.
     - The emitter's unroll guard is **10,000 iterations PER LOOP** and is env-var-only (`Y_ZK_MAX_UNROLL`). Mutating the environment from a test races the rest of the suite, so the benchmark circuit nests two loops instead.
   - **A test harness that compiles the same `.ysu` from several threads races on the `.ptx` path.** One thread reads the file while another is writing it and the JIT reports `Can't load this binary kind`, intermittently. `ptx_for` compiles each kernel once per process behind a mutex. It passed for several runs before failing, which is the worst way to find it.

9. **R1CS / BN254 Scalar Field Constraints (`zk_emitter.rs`, `zk_witness.rs`)**:
   - Circuit emission lowers expressions to BN254 scalar field arithmetic ($Fr$). Operations in ZK mode must be expressible as linear/quadratic constraint combinations; dynamic unbounded loops or unsupported non-field operations will fail constraint generation.
   - **Unroll cap, default 10,000, overridable with `Y_ZK_MAX_UNROLL`.** It is a soft OOM guard, not a structural limit - nothing in R1CS or this emitter breaks above it. Measured scaling on the polynomial circuit: 1M constraints = 1.6s / 123MB `.r1cs`; 10M = 17.7s / 9.3GB peak RSS; **31M = 70.7s / 29.8GB peak RSS / 3.7GB `.r1cs`**. Cost is linear, and **RAM is the real ceiling** - but the per-constraint figure is a property of the CIRCUIT, not of the compiler, and quoting the polynomial one is how the ceiling got overstated. Its linear combinations are 1-2 terms wide; a real circuit's are ~28. Measured after the memory work: **0.44 KB/constraint on the polynomial circuit, 1.42 KB/constraint on a Poseidon chain** - so a 46GB box holds ~105M of the former and ~32M of the latter. Before that work the dense figure was 4.84 KB/constraint (a ~9.5M ceiling), i.e. the "circuits too big for circom" claim ran out of memory close to the sizes it was about. **Always quote the dense number.** `Y_ZK_TIMING=1` reports peak RSS per phase and `Y_ZK_COMPOSITION=1` breaks the emitter's live memory down by owner. The old doc's "133x faster than circom at 1M constraints" claim was TRUE and merely blocked by this cap - re-measured with it lifted, Y is 1.60s vs circom's 245.59s, i.e. **154x**. Circom is strongly superlinear (10k->100k costs 27x, 100k->1M costs 69x); Y is linear. Noir is 12.08s at the same size. **Leo cannot compile these circuits at all** (500KB compiled-program limit; last working size 17,000 at 493KB, fails at 18,000) AND is the slowest of the four where they are comparable - at N=17,000: Y 0.0071s, Noir 0.107s, circom 0.264s, Leo 0.890s (125x). Both `leo/heavy_circuit/` (1M) and `leo/dot_product/` (100k) in this repo therefore do not build. SP1 is a zkVM and has no comparable constraint-emission step.
   - **Comparisons (`<`, `<=`, `>`, `>=`) cost ~101 constraints, by necessity.** `emit_less_than` range-checks both operands with `emit_num2bits` (booleanity per bit + one recomposition constraint, which is simultaneously the range proof) and then decomposes `a + 2^32 - b` into 33 bits; the top bit is clear exactly when `a < b`. Width is `ZK_COMPARISON_BITS = 32`, matching `I32`. An out-of-range operand makes its range check unsatisfiable, so no proof can be produced - fail-closed, never silently wrong. Do not "optimize" this back down to a handful of constraints: a field has no order, so an ordering claim without a range proof is vacuous.
     - **The 2.9x gap against circom is exactly this range check, and it was measured head to head.** `if a < b { return 1; } return 0;` is **103 constraints in Y against 36 in circom** (`LessThan(32)`, 33 non-linear + 3 linear). circomlib's `LessThan` decomposes only `a + 2^32 - b` into 33 bits and range-checks NEITHER operand - its header documents that as the caller's job. So it answers **`p-1 < 0` = 1 and `0 < p-1` = 0**, both inverted, on inputs Y refuses outright (verified with circom 2.2.3 + its wasm witness calculator; Y produces no witness). On every IN-RANGE input the two agree exactly. The extra ~67 constraints buy fail-closed behaviour, not precision - do not quote the size difference without the reason.
   - **`.r1cs` and `.wtns` are iden3-format and the whole snarkjs pipeline works** - `snarkjs r1cs info` / `groth16 setup` / `prove` / `verify` all accept Y's output, verified end to end. `Y circuit.ysu --target=r1cs --witness input.json` writes both files; inputs are matched **by name** against `fn main`'s parameters (missing or unknown keys are errors), because a file in the wrong order would otherwise prove the wrong statement. **The trap: snarkjs demands the wire layout `1, outputs, public inputs, private inputs, intermediates`, while Y allocates wires in emitter order.** `write_r1cs_binary` had always permuted its constraint terms; the first `write_wtns_binary` did not permute the witness. Both files were internally consistent, Y's own solver was happy, and `snarkjs wtns check` rejected the pair at constraint 1 - invisible internally, because every check Y runs uses Y's own numbering. Both writers now share `ZkEmitter::snarkjs_wire_map`; **if you add a third consumer of either file, it must use that map too.** `r1cs_and_wtns_use_the_same_wire_order` re-derives satisfiability in the permuted numbering so this is caught without snarkjs installed.
   - **The Solidity verifier's G2 constants are stored IMAGINARY PART FIRST, and that is not a typo.** `Fq2` is `c0 + c1*u` and every library reports `c0` first; the EVM pairing precompile at `0x08` wants `x.c1, x.c0, y.c1, y.c0`. `Groth16VerifyingKey` takes `(c0, c1)` and `emit_groth16_verifier` swaps once, at emission. Backwards gives a contract that compiles, deploys, burns the full gas of a pairing check and rejects every valid proof - no type error, no revert, nothing to grep for. Confirmed empirically: c0-first makes the precompile fail outright ("failed to create affine g point"), c1-first returns 1. Callers must pass the proof's `b` the same way (snarkjs's calldata layout). `tests/zk_solidity_verifier.rs` therefore executes the generated contract on a real EVM via `revm` after compiling it with `solc`/`solcjs` (`npm install solc`; skipped with a notice when absent, like the `ptxas` gate). **Do not replace that with a string-match test** - the failure mode it exists to catch is invisible to one. Note a corrupted proof element usually is not a curve point, so the precompile rejects its input and the contract REVERTS rather than returning false; `call_verify` treats a revert as rejection, which is what snarkjs's verifier does too. CLI: `Y --emit-verifier verification_key.json -o Verifier.sol [--name N]`; Y performs no trusted setup, the key comes from snarkjs or arkworks. `parse_snarkjs_vkey` checks `protocol` and `curve` because a PLONK or BLS12-381 key has identical field names and would otherwise yield a deployable contract that can never verify anything.
   - **Poseidon is circomlib's, and must stay that way.** `src/zk_poseidon_constants.rs` is GENERATED by `tools/extract_poseidon.py` from `circomlib/circuits/poseidon_constants.circom`, in circomlib's *optimized* layout (`C` pre-folded, length `t*R_F + R_P = 81` not `t*(R_F+R_P)`; `P` applied once before the partial rounds; sparse `S` matrices). `tests/zk_poseidon_interop.rs` pins four digests taken from circomlib's own `Poseidon(2)` through its wasm witness calculator. If they move, the hash has forked - regenerate from circomlib, do NOT update the expectations. Only **t=3 (two inputs)** is supported; other arities and non-BN254 fields are **refused**, because the previous implementation accepted everything by padding its table with a hardcoded `123456789` (it generated 60 constants where t=3 needs 195, so 135 rounds shared one value), giving a confident deterministic hash that matched no other implementation. 241 constraints vs circom's 243 non-linear + 274 linear. **The repo's vendored circomlib had a corrupted round constant** - one hex digit at index 26 of `POSEIDON_C(3)` - now replaced with official 2.0.5; every other vendored circuit differed from upstream only by a stripped licence header.
   - **`@zk_target(scheme = "plonkish")` is REFUSED, and used to be a lie.** It parsed, was stored in `active_scheme`, was printed into the `.r1cs.txt` header as `Proof Scheme: Plonkish`, and was read by nothing else - the emitter has one arithmetization and produced R1CS regardless. A user selecting a PLONKish backend got a clean compile, a success message, a header agreeing with them, and an R1CS file. Same shape as `@ZeroDrift` before it was implemented and as the Hopper intrinsics that assembled to nothing; worse here, because the artifact could be assumed to carry soundness properties of a scheme that was never used. Guarded by `tests/zk_target_claims.rs`, whose third test asserts no emitted artifact ever NAMES a scheme it did not use. **If a second arithmetization is ever added, add it to the emitter before adding it to the enum.**
   - **Bitwise / shift / integer-division operators exist now, and they are expensive.** `&`, `|`, `^` cost 98 (two `emit_num2bits` decompositions plus one AND per bit; the recomposition is linear and free). `<<`/`>>` cost 33 and take **constant shift amounts only** - a variable shift is a multiplexer over all 32 amounts, so it is refused rather than approximated. `/` and `%` cost 135. All treat values as **unsigned 32-bit**: a negative `I32` is `p - |v|`, fails its range check, and is unprovable rather than wrong. Counts pinned by `operator_costs_are_what_we_think`.
   - **`/` is integer division now, and the obvious encoding of it is UNSOUND.** It used to be *field* division (`x * y^-1 mod p`), which matches integer division only when the divisor divides exactly - `7 / 2` returned `(p+7)/2`, a 254-bit number. But the natural fix is also wrong: constraining `q * b = a - r` with `r < b` still lets a prover choose `r = 0` and `q = 7 * 2^-1 mod p`, satisfying both and proving `7 % 2 == 0`. **The range check on `q` is what closes it** - with `q, b < 2^32` the product cannot wrap the modulus, so the field equation forces the integer one. Guarded by `forged_quotient_is_rejected`; do not drop that check to save 33 constraints.
   - **`Fr` is a `Copy` `[u64; 4]` in Montgomery form (`src/zk_field.rs`), and its limbs are PRIVATE.** They are `value * R mod p`, not the value, so anything reaching past the API reads a different number with no type error. Use `to_limbs`/`to_biguint`/`to_decimal_string`/`get_bit`/`to_bytes_le`; `Ord` is by canonical value, deliberately, because the emitter constant-folds `<`/`<=`/`>`/`>=` through it. `BigUint` (still in the same file) is for parsing, one-off setup and the writers only.
     - **It was a heap `Vec<u32>`, and that one line was the entire cost of ZK compilation.** Not the field arithmetic: on a 1000-hash Poseidon chain the emitter does 4.12M `Fr::mul` + 7.81M `Fr::add`, which at the old 280ns/80ns was ~1.8s of an 8.6s emit. The other 6.8s was **356 million allocations** (1,479 per constraint, 12.69 GB) - an infinitely fast multiply would have bought 20%. Emit is now **9.35s -> 1.19s**, allocations **356M -> 5.6M**, `Fr::mul` **280ns/22 allocs -> 17.2ns/0**, and the documented 13.5x Poseidon deficit against circom is now a **1.8x lead**. `docs/zk_emit_profile.md` has the full attribution.
     - **The second-largest source was not the field or the LC layer.** `emit_poseidon` re-parsed circomlib's 144 hex constants on **every call** - `BigUint::from_hex_str` is a mul-and-add per digit, ~37,000 allocations per hash to rebuild compile-time constants. They are cached now, keyed on the active modulus (Montgomery form is defined relative to it). Emit was still 2.9s until this landed. **Re-profile after a fix, not only before it.**
     - **`optimize_circuit` (the CSE/dedup pass) was then 1.22s of the 1.86s emit and is now 0.59s of 1.19s.** Three things, none of them the algorithm: its hash buckets stored *clones* of `A` and `B` (two ~1KB Vecs per constraint) to resolve collisions against data already in `self.constraints` - they hold indices now; it bucketed with SipHash over ~2.2KB of terms per constraint when every hit is verified by full equality anyway - a multiply-xor mixer does it; and the real cost was **applying** the substitution, a `HashMap` probe per term (~7M per iteration, four iterations, almost all misses) plus a full vector rebuild - wire ids are dense, so it is an array index and a `retain` in place. The fixpoint's 4 iterations are genuine: in `h = poseidon_hash(h, y)` the part of each hash depending only on `y` is identical across all 1000, and merging one layer exposes the next. Emit is now split evenly between building constraints and this pass, so there is no single next target.
     - **Montgomery's reduction step must propagate its carry.** Koc's SOS says `ADD(t[i+s], C)` and ADD ripples; stopping after one word drops the carry for operand pairs that happen to overflow it. Every BN254 test passed with that bug in. Under Pallas, `inv(2)` and `inv(3)` came back wrong while `inv(5)` was right. **A differential test pinned to the default field cannot see this** - `zk_field`'s tests now run over all four moduli and over small elements specifically, whose inverses (`(p+1)/2`, `(2p+1)/3`) carry the most.
     - **`ScalarField::Vesta`'s modulus was COMPOSITE**, a corrupted transcription sharing only `0x40000000000000000000000000000000224698fc09` with the real value. An R1CS over Z/nZ for composite n is not a proof system, and it survived because extended-Euclid inversion happily inverts anything coprime to the modulus. `FieldParams::new` now runs Miller-Rabin over twelve bases and refuses. Do not add a field without checking the constant against the curve's published parameters.
     - `to_decimal_string` had a related disease once, peeling one digit per `div_mod(10)`, which made *formatting* the R1CS the largest phase of ZK compilation (1.3s of a 1.4s Poseidon emit). **The polynomial benchmark circuit cannot catch any of this**: its linear combinations are one or two terms wide and its coefficients are 0, 1 and 2, so it barely multiplies and never prints a large number. Benchmark against a hash circuit before believing any field-arithmetic change.
   - **This arm used to emit `BinaryOp::NotEq` instead**, so `x < y` lowered to `x != y` - `5 <= 5` was false, `5 > 3` and `3 > 5` were both true. That is a wrong function, not an imprecise one, and Groth16 proves a wrong statement just as readily. The tell was that `<`, `>`, `<=`, `==` and `!=` all emitted an identical 3 constraints. Guarded now by `comparison_operators_compute_correct_values`.
   - **Gadget wires need explicit witness recipes.** `build_witness_ir` reconstructs most wires by scanning for `a*b = c`, but an is-zero flag and its inverse witness appear in constraints that each have TWO unknowns, so back-propagation can never pin them. The `WitnessOp::{IsZeroLc, InvOrZeroLc, BitOfLc, MulLc, IntDivLc, IntModLc}` variants carry a `LinearCombination` for the forward pass to evaluate; the emitter registers them in `witness_recipes`. `build_witness_ir` also has a second-chance scan that gives any remaining single-term-output constraint a `MulLc` recipe (guarded so a constraint cannot define its own output) - without it, binding `main`'s return value (`<dense lc> * 1 = out`) left one Unknown wire, which was enough to fail the forward pass's satisfiability check and forfeit the early exit below, spending 0.427s on a single wire. Two traps if you add a gadget: (a) the fallback for an unreconstructable wire must be `WitnessOp::Unknown`, NOT `Const(0)` - `solve_r1cs_witness` treats `Const` as solved, which silently pins the wire to zero and is only visible when the right answer is non-zero; (b) any new recipe variant must be added to that function's "already solved" set, or constraints referencing it look unknown and back-propagation refuses to fire.
   - **Memory is the binding constraint on this backend, and the writers used to double it.** Three separate copies of the constraint data existed on the `--target=r1cs` path: `write_r1cs_binary` called `build_circuit()`, which deep-CLONES every `Constraint`, purely to hand a read-only view to the encoder (`ZkEmitter::view()` / `CircuitView` now); `encode_to_stream` buffered the ENTIRE constraints section in a `Vec<u8>` before writing a byte of it, when the section length the format wants up front is plain arithmetic (`3*4 + terms*36`); and it allocated a 32-byte `Vec` per TERM for the coefficient, 6.6M of them on a 237k-constraint circuit (`Fr::write_bytes_le` into a reused buffer now). **Worse, `emit_mul_lc` stored `WitnessOp::MulLc(a.clone(), b.clone())` for every product wire - a verbatim second copy of the constraint's own `A` and `B`, measured at 1096 B/constraint against the constraints' own 1135.** Its docstring's justification had expired: `build_witness_ir`'s `lc_by_output` second-chance scan reconstructs exactly that shape, and its guard (the constraint must not mention its own output) is satisfied by construction because `wire` is freshly allocated. The same reasoning removed the `MulLc` the circom front end stored for every `<==`, which is the most common statement in any circom program. Together: dense-circuit peak RSS **4.84 -> 1.42 KB/constraint**, and the emitted `.r1cs` is byte-identical throughout, which is the only reason changes this broad are safe to make at once. Verify with `Y_ZK_COMPOSITION=1`, and do not reintroduce a second copy of a linear combination without measuring it there.
   - **There is a circom front end: `Y foo.circom --target=r1cs` (`-l <dir>` for includes, `--witness in.json`).** `circom_{lexer,ast,parser,lower}.rs`; everything downstream of constraint construction is shared with Y's own language. Its acceptance test is that **circomlib's `Poseidon(2)`, compiled from unmodified circomlib source, produces circomlib's four pinned digests AND agrees with Y's native `poseidon_hash`** - see `tests/circom_frontend.rs` and `docs/circom_frontend.md`. Output/public-input/private-input counts match circom exactly on every circuit tested.
     - **circom compares `var`s as SIGNED and Y compared them CANONICALLY, so the same source computed two different functions.** `var a = 0 - 1; if (a < 1) { out <== 111; } else { out <== 222; }` - circom 2.2.3 emits a circuit computing **111**, Y emitted one computing **222**. Both compile, one constraint each, both produce a valid Groth16 proof. Invisible to a constraint count, to satisfiability, and to `snarkjs verify`; and it is CROSS-COMPILER, so a team porting an audited circuit gets a silently different one. Fixed by `signed_cmp` in `circom_lower.rs`; `tests/circom_signed_var_compare.rs`.
       - **`Fr: Ord` is deliberately canonical and must stay that way.** `zk_emitter` folds Y's OWN `<`/`<=`/`>`/`>=` through it, where both operands carry a 32-bit range check that makes canonical the right order - and an out-of-range operand is REFUSED rather than answered. The signed rule is circom's semantics, so it lives in the circom front end. `y_s_own_language_still_range_checks_instead` pins that the fix did not leak across.
       - **Only the four comparisons are signed, and that was PROBED, not read off the docs.** `\`, `%`, `<<`, `>>` and the bitwise operators all return the UNSIGNED result at `p-1` in circom. `the_arithmetic_operators_stay_unsigned` is what stops "make the whole front end signed" from passing every other test in the file - it was mutation-checked by making `IntDiv` signed, and it is the only test that catches that.
       - **The second face of the same bug is the one that blocks real circuits: a descending loop.** `for (var j = k-1; j >= 0; j--)` never terminates canonically (every field element is `>= 0`), and hit the 20,000,000-iteration unroll guard. That is the shape `circom-ecdsa` and `zk-email/rsa` are built on. Fail-CLOSED, unlike the comparison case, which is why it is asserted separately.
       - **ATTRIBUTE THE WIN BEFORE QUOTING IT - it is smaller than the headline.** On circom-ecdsa's 17 test circuits 4 compile now, but **3 of those 4 already compiled before the fix**; only `test_biglessthan_23` is attributable. The three that compiled both ways emit **byte-identical `.r1cs`**, and circomlib coverage is 31/31 before and after with identical counts on every circuit. "0 -> 4" would have been wrong in the same way the 2.80x prover figure was.
       - **Every remaining circom-ecdsa gap turned out to be the SAME BUG somewhere else, and the suite is now 17/17 (from 0).** After the signed-comparison fix the ranked list was: non-quadratic "sum of two quadratic expressions" 6 circuits, "too many indices for this array" 4, `assert` over signals 3 - and all three were Y refusing a WITNESS-domain construct because the CONSTRAINT domain could not hold it. See the three bullets below.
     - **`assert` over signals is a WITNESS-domain construct, and refusing it cost three circuits (circom-ecdsa 4/17 -> 7/17).** Y's refusal said it "is a constraint on the witness, so ignoring it would emit a circuit weaker than the source". That premise is false and is now measured: circom 2.2.3 emits **zero** constraints for `assert` over a signal - identical non-linear, linear and wire counts with and without one. So it belongs with `<--`, not with `<==`, and the argument that makes `Val::Opaque` safe applies unchanged. circom-ecdsa's `ModSubThree` says so in the source: `assert(a - b - c + (1 << n) >= 0)` sits under a comment reading "assume a - b - c + 2**n >= 0", i.e. it documents a PRECONDITION on the caller.
       - **Y does not EVALUATE it, and that is a real divergence** - circom's witness calculator aborts on a false assert and Y's solver does not. `report_unchecked_asserts` warns, modelled on `report_unsolved_witness`; going quiet is the degradation this repo refuses. A compile-time-FALSE assert is still a hard error - the relaxation covers only what the compiler cannot evaluate, and that control is what stops "delete the `Stmt::Assert` arm" from passing.
       - **The load-bearing test is an ARTIFACT comparison, not a constraint count**: the same circuit with and without the assert must serialize to **byte-identical `.r1cs`**. A count is a weaker claim - two different circuits can share one. `tests/circom_assert_is_witness_domain.rs`, mutation-verified 3/3 (revert to refusing, ignore compile-time-false asserts, treat the assert as `===`).
       - `opaque_into_assert.circom` moved from the refusal census in `tests/circom_witness_domain.rs` to a positive case, with the reason written beside it so the two lists cannot silently drift back together.
     - **Over-quadratic arithmetic is witness-domain too (7/17 -> 12/17).** `BigMult` accumulates a polynomial product in a `var` - `prod_val[i + j] += a[i] * b[j]` - far exceeding the `a*b + c` one constraint holds, then feeds it to `out[i] <-- prod_val[i]` and binds `out` with its own identity below. Y refused the ARITHMETIC. `add_vals`, `mul_vals` and `pow` now mint a `Val::Opaque` carrying the reason; `require_known` refuses at the use and names both site and cause, which is a strictly better message. Verified against circom: `out <== a*b+c*d`, `a*b+c*d === out` and `out <== a*b*c` are all still refused exactly where circom refuses them.
     - **Indexing an unknown yields an unknown (12/17 -> 17/17).** A `function` whose branch depends on a signal is havoc'd, and a `return` in a skipped branch makes it return `Val::Opaque` - a SCALAR - where the caller declared an array, so every later `v[i]` looked like a mis-indexed scalar. `secp256k1_addunequal_func` runs `mod_inv` over signal-derived values and comes back opaque wholesale. `opaque_through_index` propagates it, the same rule `add_vals`/`mul_vals` already follow. A genuine mis-index of a KNOWN scalar is still an error, and that control is what stops "never report too many indices" from passing.
     - **THE CHECK THAT MAKES THESE THREE SAFE IS A COUNT AGAINST CIRCOM, NOT AGAINST Y.** A relaxation that drops constraints still compiles and still proves - only the reference can see it. Every hermetic test here asserts circom's exact numbers (the advice fixture: 3 constraints / 8 wires; the index fixture: 1 / 3), asserts the witness SOLVES, and asserts the value comes from the author's `===` rather than the advice. Across the real suite Y lands at **0.97-0.98x circom's constraint count, stably** - `test_secp256k1_scalarmult` 1,420,100 against 1,461,156 - and it is the stability of that ratio across circuits, not its size, that rules out dropped constraints. circomlib stayed 31/31 with byte-identical counts through all four fixes.
     - **What is left is a FEATURE, not an over-strict refusal: anonymous components (circom 2.1).** `Poseidon(2)([a,b])`, `(Ax, Ay) = BabyPbk()(secret)`, `isLessThan.in <== [secret, l]`, inline `signal x <== expr`. Blocks semaphore, rln, zk-kit and zk-email/sha - 6 of the 11 real production circuits. Unlike everything above, there is no construct Y is wrongly rejecting here; the syntax is simply not implemented.
     - **`--witness` CANNOT READ A CIRCOM INPUT FILE, and `.sym` is not circom's either.** Y names `main`'s inputs `maina`, so `{"a": "5"}` - what circom's own calculator takes - is rejected with `input "maina" is missing`. Top-level `instantiate` passes the prefix `"main"` while nested components pass `"{prefix}{name}."` **with a dot**, so the top level is inconsistent with Y's own convention as well as circom's. `.sym` diverges further: circom writes `1,1,0,main.out`, Y writes `2,1,0,mainout_2` plus an extra `0,0,0,const_1` row. Compounding it, `mini_json::parse_scalar_map` is scalar-only while circom inputs are routinely arrays. **All one missing piece: a circom-compatible input binder** - until it exists, "Y compiles this circuit" does not imply "Y can run it" (`test_bigsub_15` compiles and cannot be given its inputs).        - **Soundness is the dual of the substitution pass's**: a wire in no surviving constraint is unconstrained and existentially quantified, so projecting it away preserves satisfiability both ways and cannot change the statement - provided the boundary is marked live *outright*, before any constraint is scanned. That last clause is load-bearing and is not hypothetical: **both front ends accept an input that is never read**, and such a wire appears in no constraint at all. Dropping it would leave a circuit that still compiles and still proves while presenting a different interface than the source declared. `unused_boundary_signals_survive` pins it.

Caught only by the asymmetric `Poseidon(7, 0)` vector.

Y binds its return value last, so its output wire sits above thousands of intermediates and moves.      - **Deleting constraints is the one optimisation that can silently weaken a proof**, so `tests/zk_linear_substitution.rs` does not test "did it get smaller". It tests that the reduced circuit still *binds* its output (perturb the output wire; satisfiability must break), that a contradiction stays unsatisfiable (`a <== x+1; a === x+2;` collapses to `-1 = 0`, and `constraint_is_vacuous` keeps non-zero constant identities on purpose), that **the witness the reduced circuit produces satisfies the UNREDUCED one** - wire numbering is preserved, which is why every eliminated wire is given a recipe holding exactly the expression its deleted constraint asserted - and a control asserting the pass removes anything at all. `Y_ZK_LINSUB_BUDGET=off|<n>` and `zk_emitter::set_linsub_budget` (thread-local, so a test can flip it without racing the suite) give the unreduced baseline. **That file turns wire compaction OFF on both arms** (`set_wire_compaction(false)`), because every assertion in it is stated in wire numbers and compaction renumbers by a different amount in each arm - the two settings leave different wires dead.    - **`return` was not a terminator, and `if` was not a branch — both found with Z3, guarded by `tests/zk_control_flow.rs`.** Z3 parsed an emitted `.r1cs.txt` and was asked whether any satisfying assignment disagreed with the source; both bugs are the design rule's shape — clean compile, "Compilation Successful!", artifact computing a different function.
     - **`emit_block` recorded the LAST return instead of stopping at the first** (`for stmt { if let Some(r) = emit_stmt() { last_ret = Some(r) } }`). So `return 1; return 2;` emitted a circuit computing **2**, and `if c { return x; } return y;` — the ordinary way to write a conditional — emitted one computing **`y` unconditionally**, after building and discarding the ~100 constraints of the comparison. Z3 proved the system had **no satisfying assignment with a non-zero output**: the circuit was the constant 0 and Groth16 proves that about it happily. **The LLVM backend compiles the same program to `ret i32 1`, so the two backends disagreed on what `return` means** — a cross-backend differential is the cheapest test that would have caught it.
     - **Stopping at the first return is NOT the whole fix.** `if c { return x; } REST` is `if c { return x; } else { REST }`, and the old `Stmt::If` arm substituted **zero** for the branch that does not return — right only when the next statement happens to be `return 0`, which is exactly the case anyone would test. `Stmt::If` now parks a one-sided return in `cond_ret` and `emit_stmts` multiplexes it against the tail. `the_fall_through_value_is_the_rest_of_the_block` is the test that separates the two fixes.
     - **A dynamic `if` merges with `cond * (then - else) = out - else`, which is a SELECTOR only for `cond` in {0,1}, and nothing constrained it.** `if a { return 5; } return 9;` emitted `9 - 4a`, so `a = 2` answered **1** — a value neither branch can return — and `a = 3` answered `-3`. A comparison already yields a booleanity-constrained bit so nothing reachable was wrong, but the guarantee was absent rather than unused. One booleanity constraint on the condition makes an out-of-range condition **unprovable rather than wrong**, the same fail-closed choice the comparison gadget's range checks make.
     - **The fix is now VERIFIED, and writing the proof found a third bug.** `proofs/ZkControlFlow.v` (Rocq 9.1, `coqc proofs/ZkControlFlow.v`) formalises the `return`/`if`/sequencing fragment, its operational semantics, and three lowerings. `low_correct` proves the shipped one agrees with the semantics on every program and environment; `coqchk` reports **Axioms: none**, nothing admitted.
       - **Stopping at the first return and muxing a one-sided return against the tail is STILL WRONG when the `if` is nested**, and only the proof attempt showed it: `if c { if d { return 1; } } return 7;` with `c` true and `d` false emitted **0**, because the inner `if` reported the zero its own empty tail supplied instead of telling the outer block control had fallen past it. Reproduced on the real compiler before the file was finished.
       - The correct lowering is **predicated**: every statement yields `(flag, value)`, `flag` being 1 iff it returned. Sequencing is `flag = fa + (1-fa)*fb`, `value = mux(fa, va, vb)`. The flag constant-folds when statically known, so an ordinary `return e` at the end of a function and an `if/else` where both arms return cost **nothing** extra.
       - **There were THREE sites, and the third needed something different.** `Stmt::For` discarded its body's result outright, so `for i in 0..4 { if c { return 1; } } return 9;` emitted the constant 9. That is not a wrong formula - `low_tail` handles a flat unrolled sequence correctly - it is a lowering that was never CALLED. Do not mis-attribute the fix: two sites needed a better lowering, one needed the lowering to run.

     - **Where Z3 helps and where it does not.** Proving the output was constant was instant (the constraint is literally `0 * 1 = w`). The universal soundness question for the 32-bit comparison gadget over BN254 — "is there any satisfying assignment with `out != (a < b)`" — did **not** finish, because 254-bit modular arithmetic over `Int` defeats the solver; normalising coefficients to signed form (`c - P` for `c > P/2`) helped and was still not enough. What does work cheaply is asking what the circuit computes on concrete in-range inputs with the modulus dropped, which is sound *for that question* because every value is bounded far below `P/2`. Use Z3 on the emitted artifact for "what function is this", not for full soundness.
   - **`WitnessIRGraph::topological_order` was the identity `(0..num_signals)`, and the witness solver ignored it and walked by wire index.** That is correct only when a recipe never references a higher-numbered wire - true of Y's own emitter, which allocates a wire at the moment it defines it, and NOT of circom, where `signal output out;` is declared at the top of a template and assigned at the bottom. Those wires evaluated as ZERO and the witness silently failed to satisfy its own circuit. It is a real Kahn sort now (`ZkEmitter::topological_order`), and the positional input assignment is a separate pre-pass so reordering cannot disturb it. `witness_op_deps` is exhaustively matched: a variant missing from it is not a compile error but a silent mis-ordering.
   - **`optimize_circuit` rewrites wire ids, and EVERY consumer of a wire id must be rewritten with them.** It merges two constraints with identical `A` and `B` and a single-intermediate-wire `C`, replacing the loser's wire throughout `self.constraints`. It did not replace it in `witness_recipes`, whose `LinearCombination`s are captured at EMIT time - `emit_num2bits` keeps the value it decomposes, `emit_int_div_mod` its dividend and divisor, the is-zero gadget its difference. So every gadget whose operand happened to be a common subexpression evaluated a wire the pass had just deleted, read it as **zero**, and produced a witness that did not satisfy the circuit. `let a = x * y; let b = x * y; return a == b;` - two provably equal values - was **unprovable**, as were `<`, `<=`, `>`, `>=`, `!=`, `&`, `|`, `^`, `/`, `%` on any duplicated operand, and `y * x` merges with `x * y` because the bucket hash is deliberately commutative. It surfaced only as `satisfied = false`, which reads as "this circuit is unsatisfiable" rather than as a compiler bug. `remap_witness_op` handles it, matched **exhaustively with no `_ =>` arm** so a new `WitnessOp` variant is a compile error. Guarded by `tests/zk_cse_gadget_wires.rs` - note its control asserts the deduplicated form is still one constraint SMALLER, because "stop eliminating anything" would otherwise pass every other test in the file. The audit that goes with this: the emitter's other wire-indexed state is `variables` (names, harmless), the input/output lists (excluded from replacement by the pass's own guard) and `unconstrained_hint_vars` (consumed inside `emit_circuit_entry`, before the pass runs).
   - **`zk_field.rs` is the field, `zk_emitter.rs` emits constraints, `zk_witness.rs` solves the witness.** Both are needed before anything can be proved - an R1CS alone proves nothing. The witness solver used to live inside the soundness fuzzer, which meant satisfiability was only ever checked during fuzzing and never in `cargo test`. It is library code now precisely so the fuzzer and `tests/zk_groth16_end_to_end.rs` share ONE implementation; do not fork it back.
   - **The prove path at 1M constraints is 7.5s: emit 1.34s, witness 0.10s, Groth16 setup 2.89s, prove 3.10s, verify 0.002s.** arkworks is now **80%** of it, so the remaining headroom is in the prover Y does not have. (Before the Montgomery `Fr`: 8.0s, emit 1.77s, witness 0.57s. This circuit barely multiplies, so its emit moves only 1.3x while the Poseidon chain moves 7.8x - the witness solve, which does touch dense values, moves 5.7x.) Getting there took the Barrett fix above plus two structural ones, both easy to regress: (a) `build_witness_ir` indexes `a*b=c` constraints by output wire ONCE - it used to rescan every constraint per variable, which is O(V*C) and made emit super-linear (5.96s -> 0.13s at 100k); (b) `solve_r1cs_witness` returns immediately if the forward pass already satisfies every constraint - the back-propagation sweep used to run regardless and cost 52.87s at 50k to rediscover values the 0.36s forward pass had already computed (106.61s -> 2.89s at 100k). The early exit is sound by definition, not a heuristic: an assignment satisfying every constraint is a valid witness whatever produced it. Benchmark: `cargo test --release --features zk --test zk_groth16_scale -- --ignored --nocapture`.
   - The proof test is the real correctness gate for this backend: it runs Groth16 over BN254 through arkworks, asserts an honest proof verifies, a tampered public input is rejected, a perturbed witness fails satisfiability, and that Y's own modulus equals the true BN254 one. String-matching the emitted `.r1cs` cannot catch a wrong field or a mis-numbered wire; this can.
10. **The Generative Differential Fuzzer (`src/zk_fuzz.rs`, `tests/zk_fuzz_differential.rs`)**:
   - **`fuzz/` had eight targets and not one of them could have found the four control-flow bugs, or the two the new fuzzer found.** Worth reading as a catalogue of ways a fuzzer can be decorative: `fuzz_zk_emitter` and `fuzz_zk_soundness` feed **raw bytes to the lexer**, so the chance of ever forming a program with an `if` and a `return` in it is negligible; `fuzz_differential` was **not differential** (one `ConstDecl`, no control flow, and it compared nothing — it asserted the CPU emitter's output string was non-empty); and `fuzz_zk_soundness` reported every finding with `eprintln!` and **never panicked**, so libFuzzer could not see a failure and a week-long run over a backend computing the wrong function would exit 0. Its under-constrained-signal scan was worse still: the helper returns `Ok(count)` on every path, so the `if let Err(..)` around it was dead code and the scan had never reported anything in its life. **The common thread is that they all checked the compiler did not crash, never that it emitted the right circuit** — and every bug in this backend's history compiled cleanly and produced a satisfiable circuit.
   - The replacement generates **well-formed programs from a grammar** (100% parse rate by construction) and checks them with three oracles. It found two bugs in its first run, in two different subsystems.
     - **Oracle 1, an independent interpreter.** Written against `zk_fuzz`'s own IR, *not* against Y's AST, so the path under test (render to source → lex → parse → emit → solve) shares no code with the oracle and a parser bug is visible. Walking the AST the parser produced would have hidden the parser bug it actually found.
     - **Oracle 2, a metamorphic constant-folding check, and it is the strongest one because it needs no reference implementation.** The same program is rendered twice — once taking its inputs as parameters, once with those inputs substituted as literals — and the two must agree. That is what caught the constant-fold range-check family: the compiler answered `<unprovable>` for values passed as parameters and `0` for the identical values written as literals. **An oracle with no model cannot be wrong in the same direction as the model.**
     - **Oracle 3, parse failures, graded separately from semantic refusals.** Collapsing them was a real mistake: the parser bug surfaced only as an "over-refusal", which is not gated because a semantic refusal is fail-closed and legitimate — so reverting the parser fix passed the entire sweep. **Mutation testing is what exposed that**, not review.
   - **The fuzzer is mutation-verified, and two of five mutations were initially MISSED.** `tools`-style verification lives in the session log rather than a script, but the result is pinned by the tests: reverting either new fix, and re-introducing original bugs 1, 2 and 4, are all caught. The two initial misses had one cause — I had restricted generated `if` conditions to comparisons to simplify the model, which removed the only shape that reaches both the booleanity constraint and the `if <ident> {` parse. **A generator restriction made to help the oracle silently deleted two bug classes.** A bare *parameter* condition restored both and is safe for a stateable reason: a parameter is never constant-folded, so no branch can be statically pruned and the model stays exact.
   - **`minimize` is delta debugging over the IR, not the text**, so every candidate is still a well-formed program. It took a 40-line generated counterexample to `if p0 { } return 59;` — four lines — which is the difference between attributing the parser bug and guessing at it. Do not skip it: two hypotheses about that finding were wrong before the minimiser settled it.
   - **Known limitation, confirmed with a minimal repro and NOT a bug: a range check in a branch the input does not take still constrains the witness.** A circuit has no control flow, so both arms are emitted and `emit_num2bits` is unconditional. `if p0 < 5 { return 1; } else { return (0 - p0) < 3; }` at `p0 = 1` takes the first branch and is **unprovable**, because the other arm underflows. This is fail-closed and accounts for ~74% of the sweep's over-refusals (the remainder are the same cause reached through paths the attribution approximates). Fixing it means predicating range checks on the branch flag — a real design change with a real constraint cost, not a typo.
   - **The `cargo test` gate is what runs and what found everything; the `cargo fuzz` target is UNRUN.** `cargo-fuzz` is not installed here and there is no nightly toolchain, so `fuzz/fuzz_targets/fuzz_differential.rs` has never been executed — it is written against the same shared `check_bytes`, but do not report it as verified.
   - Sweep status at 20,000 programs: **0 wrong-value, 0 parse failure, 0 folding divergence, 1062 over-refusal.** `Y_FUZZ_SEED=<n> ... -- dump_seed --ignored --nocapture` reproduces and minimises any one of them.

11. **The Parser's Struct-Literal Ambiguity (`parser.rs`)**:
   - **`if p0 { }` did not parse.** `p0 { }` is a well-formed empty struct literal, so the condition parser swallowed it and the `if` was left looking for its block — reporting `Expected '{' to begin block but found Return`, pointing at **the statement after the `if`**. That misdirection is why it survived: it reads as a mistake on the line below.
   - Fixed the way Rust fixes it, with a `no_struct_literal` flag set while parsing the condition of `if`/`while` and a `match` scrutinee, and cleared again inside `(...)` and call arguments where a `{` cannot be a block header. Only the empty-body case was reachable — the heuristic's other arm needs `ident :` after the brace, which no Y statement begins with.
   - **The flag was set at three sites and a `for` header is a fourth**: `for i in 0..n { }` swallowed the empty body as the struct literal `n {}` and reported the same misdirected `Expected '{' to begin block`, pointing at the statement after the loop. `end` and `step` can reach a `{`; `start` cannot (it is always followed by `..`) and is guarded anyway, which the tests label as a confirmation rather than a guard. Neither fuzzer could find it either — the generator emits `for i0 in 0..1 { ... }`, a literal bound with a non-empty body, so it cannot write the program. **This is the third time in one sweep that a correct guard was consulted at a subset of its sites** (see the `takes_reference` and `linear_tracker` rows in the design-rule table); enumerate the SITES, not just the match arms.
   - `tests/parser_block_header_ambiguity.rs` covers all four sites and is deliberately NOT feature-gated. The original half lives in `tests/zk_gadget_range_and_parsing.rs` behind `--features zk`, so the default `cargo test` was not checking the parser at all.
   - **It was found by the ZK fuzzer, and nothing about it is ZK.** A generative fuzzer over the surface syntax reaches the front end too; this is the argument for generating *programs* rather than fuzzing one backend's entry point.

12. **Self-Hosted Compiler Parity (`self_hosted/`)**:
   - `self_hosted/` contains Y compiler components written in `.ysu`. When modifying AST structures or grammar in `src/`, check for corresponding updates needed in `self_hosted/`.
   - **Nothing in this repo built it, and 6 of its 10 files did not parse.** No test, no script, no Makefile target - it was named only in a documentation file, so it had rotted invisibly. Two mechanical causes, both now fixed: `parser.ysu` had a `while parsing_body {` header deleted and a 98-line duplicate of `parse_stmt`'s tail left dangling after the method's closing brace (five files `import parser`, so one deletion caused five of the six failures), and `type_checker.ysu` used **`step` as a variable name, which is reserved** by the `for i in a..b step N` syntax - the same collision as the generated BN254 temporaries hitting `U16`, found the same way, by a name that reads as perfectly ordinary. The parser's message said only "Expected identifier after let"; it names the word and the reason now.
   - `tests/self_hosted_parses.rs` is the gate. It asserts **parsing only**: the files still report `[Strict Safety] Variables in safe blocks must be explicitly initialized` for `lib.ysu`'s stub accessors (`fn get_Token(..) -> Token { let d: Token; return d; }`), which is the compiler correctly refusing a genuinely uninitialized read. Implementing those stubs is self-hosted work, not a compiler bug, and pinning "compiles cleanly" would pin the stubs.
   - **`let p: P = P { ... };` did not type-check** for a declared struct `P`: `resolve_type` read the variable table (type aliases) and never `self.structs`, so an annotated binding was `Type mismatch in let assignment` while the identical unannotated one compiled. The self-hosted compiler annotates ~340 `let`s with struct types, which is how it surfaced.

## Design Rule: unhandled AST nodes in soundness-critical passes MUST reject

**In any pass whose output is a correctness claim, an unhandled AST node is a hard error — never a silent identity, no-op, or "close enough" substitution.** A pass that silently approximates produces the paperwork of a proof without the proof, and the failure is invisible: the build goes green.

This rule is written down because the same bug has now been found seven times in this repo, each time as a `_ =>` arm that guessed instead of refusing:

| Site | Silent fallback | Consequence |
|---|---|---|
| `zk_emitter` comparisons | `Lt \| Le \| Gt \| Ge` → `BinaryOp::NotEq` | `5 <= 5` false; Groth16 proved it anyway |
| `build_witness_ir` | unreconstructable wire → `Const(0)` | wire pinned to zero, only visible when the answer wasn't zero |
| `expr_to_smt` | `_ => "0"`, `_ => "+"`, `_ => opnd` | calls/indexes/floats became `0`; `x & y` proven as `x + y`; `*p` proven as `p` |
| `trace_body_statements` | `_ => {}` | a violating assignment inside an `if` was invisible, so a false invariant compiled clean |
| `type_checker` loop bounds | unknown range → `Interval { min: 0, max: 999999 }` | `for i in n..3` over a 2,000,000-element array compiled clean |
| `ptx_emitter` `Expr::Call` | member callee → `_ => "".into()` | `pipe.wait(t)` emitted nothing; the await the linear tracker proves is discarded |
| `linear_tracker` control flow | `if`/`for` did not change tracker state | a conditional await, and one copy awaited N times, both accepted |
| `ptx_emitter` `Expr::BinaryOp` | `_ => "add.s32"` and `_ => "add.f32"` | `a < b`, `a & b`, `a >> b` and `a % b` all emitted an ADDITION — so `if a < b` in a kernel body could never have worked |

| `ptx_emitter` `mma_sync` | 3 fragment args discarded; one fixed `mma.sync` with wrong register counts | `%f1` outside the declared `.reg .f32 %f<1>` pool and 2 accumulator regs where m16n8k16 needs 4 — **the `wgmma_async` bug, missed by the sweep that fixed it** |

| `quantization_pass` conversion table | `_ =>` → `emit_scalar_fallback`, which emits two PTX **comments** and no instructions | 57 of 64 precision pairs "converted" by leaving shared memory holding the SOURCE bits, on the cross-pipeline barrier the tensor core reads |

| `auto_vectorize::is_128bit_aligned` | `_ => true` | an index expression the pass does not recognise is declared 16-byte aligned, licensing a vector load with no alignment proof (dead code — see below) |
| `rocm_emitter::emit_expr` | `_ => self.new_vgpr()` | an unhandled expression yields a fresh **uninitialised** register (dead code — see below) |
| `llvm_emitter::emit_coerce` | narrow→wide always `sext`, including from `i1` | `let t: I32 = a > b;` was **-1**, so `t * 5` was -5 — invisible in a condition, wrong wherever a comparison is a value |
| `llvm_emitter::emit_coerce` | narrow→wide always `sext`, ignoring unsignedness | `let x: U32 = 3000000000; let y: U64 = x;` gave `0xFFFFFFFF_B2D05E00` — gotcha #7 in its THIRD backend |
| `type_checker::resolve_type` `Type::Generic` | unknown base → `SemanticType::Unknown`, then `llvm_emitter` `_ => "ptr"` | `struct Z { a: Nonsense<F32, 8> }` compiled to `{ ptr, i32 }`; `ptr` is legal LLVM so nothing downstream could object |
| `type_checker::resolve_type` `Type::Reference` | → `SemanticType::Unknown` | `let r: &F32 = &x;` with `x: I32` compiled clean; `Unknown` is *exempted* from the mismatch check |

| `type_checker::resolve_type` `BlockTile` size | non-literal → `128`, at two arms | `SemanticType` derives `PartialEq`, so two differently-sized tiles compared **equal** |

**"Compilation Successful!" was printed BEFORE the backend dispatch ran, so every backend failure was announced under a green banner.** `--emit-native` on an `if`, `--target=r1cs` on an out-of-range comparison operand: banner, then `[4/4]`, then a red error, then `exit(1)`. The exit code was always right and no artifact was ever written, so this is the *reporting* half of the failure shape rather than a correctness bug - but it is the same reading error that `wgmma_async`, the plonkish scheme flag and the silently-ignored `--c` all depend on. The pre-dispatch line is `Front-end analysis complete.` now and the real banner moved to the end of `main`, which every successful path falls through to (no arm exits 0).
  - `tests/success_banner_means_success.rs` pins the **biconditional**: the banner appears iff the exit code is 0. "Never print it" satisfies half of that and is useless - the success control is what makes the file mean anything, the same shape as `ordinary_loop_bodies_still_verify`. Mutation-verified in both directions.
  - **It immediately exposed four tests in three files using the banner as a proxy for "the front end accepted this program"** - they compile stubs calling undeclared functions, or use `match`, which the PTX backend refuses by name. They assert on the front-end line now. Their NEGATIVE assertions got STRONGER in the same move: `!contains(banner)` was previously satisfied by a program the front end ACCEPTED and a backend then refused, which reads as "the front end rejected it".

**There is a cross-backend differential now (`tests/backend_differential.rs`), and it found a bug on its first run.** This document already said, about the ZK `return` bug, that "the LLVM backend compiles the same program to `ret i32 1`, so the two backends disagreed on what `return` means — a cross-backend differential is the cheapest test that would have caught it". Nobody had written one. It generates straight-line integer programs, compiles them through **both** `--emit-llvm` and `--emit-native`, runs both binaries, and compares: **6 of 40 disagreed**, all on comparison operators, because `emit_coerce` sign-extended the `i1` an `icmp` produces. `--emit-native`, the ZK emitter (booleanity-constrained) and `cpu_emitter` (a Rust `bool`) all answer 1; LLVM alone answered -1. **A differential is the only test shape that can find "which of my backends is the odd one out" without anyone deciding in advance what the answer should be.**
  - **A process exit status carries 8 bits**, so one program compares one byte of a 32-bit answer. Each generated program returns `(expr >> s) & 255` for `s` drawn from {0, 8, 16, 24}, spreading the comparison over the word. This leans on `>>` and `&` agreeing, which is itself under test — and a bug present *identically* in both backends is invisible to any differential, which is the standing limit of the technique.
  - **Refusals are counted, not skipped.** `--emit-native` refuses everything outside its subset, so a generator that drifted out of it would leave the differential comparing nothing and passing. `the_corpus_is_not_all_skips` asserts a floor (currently 40/40 compare, 0 refused). Same lesson as `feedback-null-metrics-pass-dead-components`.
  - Its two tests raced each other on identical temp-dir names and presented as an intermittent failure **with no disagreement listed** — the `.ptx` race from the GPU harness, in a new file, on the first run.
  - **Deepening the generator found a second bug the flat one could not.** `emit_coerce`'s promotion only runs when the two operand types DIFFER, so two comparisons combined by a third operator stayed at `i1`, where LLVM reads `1` as -1: `((v == v) < (v > v))` emitted `icmp slt i1 1, 0` and answered TRUE. `add i1` wraps mod 2 as well, so `(a > b) + (c > d)` could only ever be 0 or 1. 400 flat programs had already passed clean — a flat program cannot put a comparison in an operand position. **The fix is two sites**: widening in the emitter alone left `infer_type` still reporting `i1`, so the caller emitted `zext i1 %t` on an i32 register and clang rejected the module.
  - That in turn exposed the vacuous-skip hole in `tests/llvm_integer_widths.rs`, whose `run_program` returned `None` for both "no clang" and "clang rejected the IR" — so the `infer_type` mutation initially SURVIVED with the whole file green. Hardened the same way `llvm_control_flow.rs` was. **Three files have now had this exact harness bug; check it in any helper that returns an `Option` for a build.**

**`tests/zk_llvm_differential.rs` is the same idea reaching CONTROL FLOW, which the native pairing cannot** (the native backend has no branches). The same body is compiled to a binary by LLVM and to an R1CS circuit solved for its witness by `zk_emitter`, with the inputs as PARAMETERS on both sides so neither can fold a condition away. Field-vs-`i32` differences are designed out rather than tolerated: no subtraction is generated (`3 - 5` is `p - 2` in the field), and every binding is masked to 16 bits so no product can pass `i32`.
  - **It is validated by re-introducing each of the four historical control-flow bugs, not by assertion.** "`return` not a terminator" and "`Stmt::For` discards its body's return" are CAUGHT. "The condition is never constrained to a bit" is NOT, and that is a confirmation rather than a hole — every generated condition is a comparison, which already yields a booleanity-constrained bit. The Coq-found one has no shape left to restore.
  - **The `for` bug was missed twice before it was caught**, which is the transferable part. First the generator emitted no loops; then it emitted loops whose guard compared a raw parameter (0..199) against an index below 5, so the return inside could never be taken and the mutation stayed green. A branch that cannot be reached tests nothing — `feedback-exercised-is-not-covered`, one level down.
  - **Building it found a live bug in a feature the compiler was recommending: `while` with `@max_iterations(N)` computed the wrong function, and is now REFUSED.** The bounded form unrolled N times behind an active mask (`active_{i+1} = active_i * cond_{i+1}`, every mutated variable muxed on it) and failed three ways depending on the bound. `while i < p0 { acc = acc + 3; i = i + 1; }`, solved for p0 = 0..3: **`@max_iterations(1)` gives 3, 3, 3, 3 where the answer is 0, 3, 3, 3** — the body ran although the condition was false on entry, the circuit is SATISFIABLE, and Groth16 proves it; `@max_iterations(2)` is **correct**; `@max_iterations(4)` is unsatisfiable for every non-zero input. **That N=2 is correct is how it survived** — it is what anyone probes first. Refused rather than repaired, and the lowering kept as dead code behind the refusal.
    - Its unit test asserted the emitted text contains `active_mask` and that constraints exist. Both hold perfectly for a circuit computing the wrong function: **a substring test pinning a broken construct as a regression guard**, the `wgmma...s4` mistake again, in the backend where the artifact is a proof.
    - The docs advertised it in two places and are corrected with the measured table rather than quietly edited. `@max_iterations` still parses for other backends.



**`SemanticType::Unknown` is not a neutral answer in `type_checker`, and three arms were returning it.** The `let` arm reads `Unknown` as "adopt the annotation" and the assignment arm exempts it from the mismatch check outright — so `Unknown` on *either* side of a comparison silently suppresses it. `Type::Reference` and every `Expr::UnaryOp` both returned it, which meant `let r: &F32 = &x;` with `x: I32` was unchecked on both sides. **Fixing either alone buys nothing**, and mutation shows worse than nothing: repairing only the annotation makes the CORRECT case (`&I32 = &x`) start being refused. When a check compares two derived values, both derivations are the fix.

**The five newest rows are all in code that NOTHING GATED, and they split into two kinds.** `quantization_pass` is live — it sits on `coprocessor_scheduler`'s `needs_quantization` path, the same `cross_pipeline_edges()` loop as the two `ir_grapher` rows below, so the fix there made these fire more often. `auto_vectorize` and `rocm_emitter` were dead and are deleted.

**A decorative code generator passes every test this repo had.** Gotcha #8 says PTX tests must assemble rather than string-match; that is necessary and not sufficient, because *comments assemble* and so does `mov.u32 %qr, 0`. Of the seven precision pairs the quantization pass claimed, four emit a real `cvt` instruction and are still wrong — they never emit a **store**, so shared memory keeps the source bits and the tensor core reinterprets them. The assertion that separates real from decorative is therefore about the output's EFFECT, not its vocabulary:

    strip comments and blank lines; require what remains to contain `st.shared`

That one line found all five. `tests/quantization_pass_refuses.rs` pairs it with the refusal census (54 unimplemented pairs must be refused BY NAME) and a control (an identity conversion must be a legal no-op, not a refusal — refusing everything unimplemented is sound and useless, the same shape as `ordinary_loop_bodies_still_verify`).

**`run_all_optimization_passes` had zero callers and ran five passes, none of which did what its name said** — two renamed calls to intrinsics that exist in no backend, two counted and returned, one mutated nothing. They are deleted rather than fixed, because every one is superseded by something real (`bank_conflict.rs` for the swizzle, `block_ptr2d_load_v4` for the vector loads, `CpuShapeDispatcher` for the classification). **The mechanism that hid all of it is that 31 of the crate's modules open with a blanket `#![allow(dead_code)]`**, and `pub` items in a `pub mod` are never dead-code-flagged anyway — so neither rustc nor any test could have said a word. A liveness probe (run the pass, compare the AST before and after) is four lines and settles it; write one for any pass you cannot point at a caller for.

**The two `ir_grapher` rows are the newest, and they are the first found in a pass whose output is a SCHEDULE rather than an artifact.** Nothing downstream can catch them: the emitted PTX is well-formed, `ptxas` accepts it, and the kernel launches — it just overlaps two ops that depend on each other. Measured on `--emit-coprocessor` before the fix, the same program written two ways:

    b  = bvh_traverse(a);   RT 2  Tensor 1  cross-pipe 1  412 cycles  1 sync barrier
    b += bvh_traverse(a);   RT 1  Tensor 1  cross-pipe 0  212 cycles  0 sync barriers

**The barrier count is the real consequence, and it is worse than a bad cost estimate.** `coprocessor_scheduler::schedule` iterates `graph.cross_pipeline_edges()` to emit `SyncBarrier`s, and that same loop sets `needs_quantization`. Zero edges therefore means the emitted kernel has **no synchronisation between the RT producer and the Tensor consumer** *and* never converts FP32 to FP16 for the tensor core — a race and a type reinterpretation, from writing `+=` instead of `=`. Check what CONSUMES the structure a pass builds before ranking the severity of a hole in it.

`analyze_stmt` handled 10 of 17 `Stmt` variants; the four that mattered were `CompoundAssign` (no node, no edge, and **`var_producers` left pointing at the previous producer** — so a later consumer wires to a stale node), `Match` (arm bodies never walked — the same site-not-variant gap the linear tracker had for `match`), `Return` (its expression still executes), and `ClockDomainBlock` (every other block-carrying statement was walked). `wire_expr_dependencies` handled 5 of 17 `Expr` variants and dropped four sub-expression carriers, `StructLit` among them — the same variant that hid the `takes_reference` gap.
  - The regression test asserts an **equivalence, not a count**: `x += e` is `x = x + e`, so the two must graph identically. A count would need updating whenever the cost model moves; the equivalence holds as long as the language does. Gated by `tests/ir_grapher_dependency_coverage.rs`, mutation-verified 7/7.
  - **Its first version was named `a_read_through_a_struct_field_is_still_a_dependency` and never built a struct literal** — it asserted on a plain call and passed with the `StructLit` arm mutated back to `=> {}`. Caught by running the mutation, not by reading the test. A test named for the case it does not exercise is worse than no test, because it retires the question.

**The two rows above `native_emitter` are one finding in two layers, and the order they were found in is the point.** `ptx_emitter::emit_stmt` had no `Stmt::While` arm, so a `while` loop in a kernel emitted NOTHING — and no `ptxas` gate could see it, because a missing instruction assembles perfectly (gotcha #8 again). It survived because it was **unreachable**: `check_stmt` clears the interval of every body-assigned variable before verifying a loop, and the INITIATION obligation is about the state on ENTRY where those intervals are still true, so every `@invariant` naming a body-assigned variable failed — and a `while`'s induction variable always is one. An `@invariant` is mandatory outside `unsafe`, so no `while` loop in safe Y reached a backend at all. `tests/math.ysu` and `tests/safe_test.ysu` were both refused by it; the corpus went **78 compile / 5 refuse to 80 / 3**. Fixing the front-end check is what made the backend gap live, within the same hour.
  - The fix is a snapshot of the pre-loop intervals threaded into the initiation query **only**, and that narrowness has its own test. A fact true on entry is not true after an iteration: leaking it into preservation proves FALSE invariants — `@invariant(acc <= 1)` over `for i in 0..4 { acc = acc + 1; }` from `acc = 0` compiles clean under that mutation, and `acc` reaches 4. The tests assert WHICH PHASE rejects a program, not merely that one does; reverting the fix moves three programs from "preservation" to "initiation", which a pass/fail assertion cannot see.
  - `while` is lowered exactly like `Stmt::For` (test at the top, branch out on false, body, branch back) and `ptxas -arch=sm_89` accepts it. `break` and `match` are refused by name. `break`'s emitter arm is a **confirmation, not a guard** — the invariant verifier refuses a `break` in a loop body first, so it cannot reach the backend today, and its test asserts the end-to-end property instead.
  - Two more in the same arm: `Stmt::Return(_, _) => {}` dropped a bare `return;` (an early exit that silently did not happen — it emits `ret;` now, and `return <expr>` from a void kernel is refused), and the `if` condition fell back to `"%r0"`, i.e. parameter 0, when `emit_expr` returned empty.
  - **The other backends were checked for the same gap and `llvm_emitter`'s `while` is correct** — clean IR, terminates, right answer — which is why `tests/llvm_control_flow.rs` RUNS it rather than reading the IR. Two harness weaknesses in that file were found by mutation and not by review: returning "could not build" for both *no clang* and *clang rejected the IR* made every case skip vacuously (dropping the loop's back-edge leaves a block with no terminator, and all three tests passed), and dropping the loop BODY makes the program run forever — a hung test rather than a failing one, so the child runs under a deadline now.

**The `native_emitter` row is the integer-width gotcha in its THIRD backend** — PTX first, then `llvm_emitter`, now here — which is the strongest evidence yet for the rule that a gotcha is a property of the *pattern*, not the module. It is also the only one of the three that produced a runnable artifact. Two distinct defects, and the second is why a literal range check alone is not the fix: `let a: I64 = 100000; let b: I64 = 100000;` has **no large literal in it**, the values fit in 32 bits and the product does not, so the declared type is the lie. Both are refused by name (`check_type_width` on `let`, parameters and return types; an `i32` range check on `Expr::IntLit`), because widening the datapath is a feature — REX.W on every instruction, `movabs` immediates — and not a typo. Guarded by `sixty_four_bit_types_and_literals_are_refused`, whose control `thirty_two_bit_programs_still_compile_and_run` is what stops "refuse every integer type" from passing. `cpu_emitter` was checked for the same shape and is clean in the fail-closed direction: its `_ => name.clone()` turns `I64` into the Rust identifier `I64`, which rustc rejects.

**The two `zk_emitter::emit_stmt` rows are the same sweep reaching the backend where this costs the most.** Ten `Stmt` variants were handled and `_ => {}` swallowed the rest, so the emitter disagreed with ITSELF about what a program meant: `x = x + 5;` emitted `(5 + w_1) * 1 = w_2` and `x += 5;` emitted `w_1 * 1 = w_2`. Both compiled clean, both solved to a satisfying witness, and one of them proves a statement the author did not write. `CompoundAssign` is desugared to `Stmt::Assign` rather than reimplemented - `x op= e` IS `x = x op e`, and `Stmt::Assign` already carries the running-sum fast path. `SafeBlock`/`GhostBlock` emit their bodies and PROPAGATE the predicated `Ret` (discarding it is the `Stmt::For` row again, in a different statement). `chisel` and `@clock_domain` are refused by name; `TypeAlias` and `CompileTimeAssert` emit nothing with the reason written down. No `_ =>` arm remains.

**The generative fuzzer could not write the program that exposes it, and that is why it survived.** `FStmt` had `Return`, `Assign`, `If` and `For` and no compound assignment, so oracle 1 had nothing to disagree about - the exact lesson already recorded one section down about restricting `if` conditions, found again. The fix costs nothing in the IR: the generator now builds about a third of its assignments in the `x = x op e` shape and `render` spells that `x op= e`, so the interpreter, the minimiser and the refusal analysis all still see ONE statement with one meaning. Verified both ways - `the_generated_corpus_is_not_vacuous` asserts compound assignments actually appear, and re-introducing the dropped arm makes `generated_programs_agree_with_their_semantics` fail with `WrongValue`.

**The `type_checker` and `linear_tracker` rows are the ones before those, and they are a different shape again: not an unhandled node but an unhandled SITE.** `takes_reference` is the single assumption the whole `@invariant` SMT model rests on — Y has no way for a callee to write a caller's local integer scalar unless handed a reference — and it was correct, exhaustive-ish, and *called from one place*: the top-level `Stmt::Expr` arm of `trace_body_statements`. So `bump(&i);` was refused and `if i >= 0 { bump(&i); }` was accepted, which is the `nested_if_cannot_hide_a_false_invariant` bug one level down, in the guard that fix installed. `stmts_take_reference` now asks the question of the whole loop body — of the UNSLICED body, because `slice_body_for_invariant` decides relevance from names and a reference is exactly what invalidates that reasoning. Five sites were live: inside a branch, an assignment's right-hand side, a `let` initialiser, a `match` arm, and a struct literal in an argument.

**The same shape was then found in `linear_tracker`'s wiring, which is the point of writing it down.** The conditional-depth fix that made `if n { pipe.wait(t); }` a linear-type error wired `Stmt::If`, `Stmt::For` and `Stmt::While` into the tracker and stopped there - so `match n { _ => pipe.wait(t) }`, the same missing-await race, compiled clean. `Stmt::Match` raises the depth now. A single irrefutable arm is not really conditional and this over-approximates it, which is free: a match arm's body is one `Expr` (the parser builds no `Expr::BlockExpr`), so "copy and await inside the same arm" is not a program that can be written, and there is nothing inside an arm for the over-approximation to ban. The control is therefore a `match` BESIDE a correct transfer, not inside one. `@ghost` was checked and is not a branch - every emitter lowers it to an ordinary block.

**The nested-loop arm is a CONFIRMATION, not a guard, and the mutation run is what separated them.** Deleting `Stmt::For`'s body traversal leaves the whole suite green, correctly: `check_stmt` requires an `@invariant` on every loop outside `unsafe`, so a nested loop is verified in its own right and catches its own body first. The arm is kept regardless — this check must not depend on a rule a different pass happens to enforce — and the test says so, rather than being read as pinning it. Six of seven mutations were caught by exactly one test each.

**The five host-backend rows are the ones before those, and `native_emitter` is the one to read: it is the only place in this repo where the silent substitution produced a RUNNABLE ARTIFACT.** `--emit-native` wrote a 188-byte executable ELF, printed "Compiled to native ELF executable!", exited 0, and returned 9 for `9 / 2`. Every other instance of this bug class produced text - PTX that `ptxas` might reject, an `.r1cs` a prover would still accept, LLVM IR clang would compile. This one handed the user a binary. Two lessons beyond the usual one. **The bug was in three independent `_ => {}` arms and fixing any one alone leaves the backend wrong**, which is why `every_integer_binary_operator_computes_its_own_operation` includes `a - b` - `Sub` *was* implemented and still returned 0, because both operands resolved to the same local. Testing only the unimplemented operators would have attributed the failure to the wrong arm. And **both new test files needed their refusal fixture replaced**: the first used a construct the PARSER rejects, so the assertion held for a reason unrelated to the backend and deleting the refusal entirely left it green - the `feedback-mutation-holes-hide-behind-later-checks` shape again. Each case now asserts on its own diagnostic string, so a fixture stopped by an earlier pass fails instead of passing.

**The six `ptx_emitter` intrinsic rows are the newest, and they are the same bug counted 47 times.** Every affected lowering reads its operands as `if args.len() >= N { emit(args[N-1]) } else { "%r0".into() }`, so a call with too few arguments does not fail — it substitutes *whatever happens to live in that register*, which is another variable in the same kernel. Two outcomes: the register has the wrong type and `ptxas` rejects the module **after** the compiler printed a green success banner and exited 0, or it has the right type and the kernel silently computes with the wrong operand. `required_arity` now gates the whole family before any lowering runs.

Two details worth keeping. **The required count is the last position whose fallback is a REGISTER, not the parameter count** — several of these have genuinely optional trailing operands defaulting to a *literal* (`block_tile_store`'s bound falls back to `128`, which is a defensible default), and requiring the full list broke `supported_intrinsics_emit_assemblable_ptx` on the first attempt. And **only `block_ptr2d_store` is called by any kernel in this repo**, always with its full seven; the other ~20 are reachable from the surface syntax and used by nothing, exactly like the Hopper intrinsics above. That is what made the gate safe to add at once, and it is also the tell that this surface was never exercised.




**The two `llvm_emitter` rows are gotcha #7 found in the OTHER backend.** CLAUDE.md has said since the PTX integer work that "integer literals are typed by VALUE, not fixed at I32" — and `llvm_emitter::infer_type` still returned `"i32"` for every literal. Measured, both compiling cleanly and running to completion:

    let a: I64 = 4294967296; if a > 0 { 1 } else { 0 }   ->  0   (truncated)
    let a: I64 = 3000000000; if a > 0 { 1 } else { 0 }   ->  0   (sign-extended)

`clang` accepts `store i32 4294967296` and `sext i32 3000000000 to i64` without a word. **When a gotcha is written for one backend, grep the others for the same shape before assuming it is backend-specific** — the same lesson `mma_sync` taught one section down, and the reason `tests/llvm_integer_widths.rs` now RUNS the binary rather than reading the IR.

**And the first version of that test was itself vacuous, caught only by mutation.** It compared `U64 4294967296 > U64 2147483648`; with the fix reverted both truncate — to `0` and `-2147483648` — and `0 > -2147483648` is still true, so two wrong values agreed and the test passed. It compares against a constant now. Cross-check a suspect value against something that does **not** go through the suspect path.

**The general case is the last row but one, and it is the one to fix first in any emitter: `emit_expr` returning `""` for a name it does not know.** Callers splice that straight into instruction text. A typo'd or nonexistent intrinsic in *argument* position produced `setp.lt.u32 %p1, , %r0;` and a success banner; it was noticed only when the result happened to be bound with `let`, which has its own guard. A user-defined `fn` called from a kernel lands there too — this backend cannot lower one, and the gap is now named at the call site.

**The gate had to be added TWICE, and that is the transferable part.** `Expr::Call` matches its callee, and *both* the `Ident` arm and the `Path` arm carry their own register-aliasing fallbacks (`BlockTile::load`'s offset falls back to `%r0`, its value to `%f0`). Gating only the identifiers left the paths open and every test still green. **When a bug is in a match arm, check the sibling arms before believing it is fixed** — the same lesson `optimize_circuit` taught about downstream consumers, one level up.

**`mma_sync` is the one to read if you read one.** It is the same defect as `wgmma_async` — arguments ignored, a hardcoded instruction, registers outside the declared pool — and it survived the sweep that deleted the Hopper surface *because it is not a Hopper intrinsic*: it sits in the reachable `--emit-ptx` path, and the `coprocessor_*.ysu` kernels that call it are compiled by a **different emitter** (`coprocessor_scheduler.rs`) that builds its own correct `mma.sync`. So the working path masked the broken one. When you fix a family of intrinsics, grep for the *shape* of the bug, not the names in the family.

**Two of these were pinned by tests that asserted the wrong behaviour.** `block_arange` was in `supported_intrinsics_emit_assemblable_ptx`'s SUPPORTED list, and `test_rust_triton_parity.rs` asserts the emitted PTX contains `%tid.x`. Both pass with the argument-discarding lowering, because `mov.u32 %r, %tid.x` assembles perfectly and is simply the wrong value — the limit an assemble-only gate has, stated in gotcha #8 and demonstrated again here. The nullary form is legitimate and still supported; only a call that would silently discard its arguments is refused.

**The `zk_emitter` constant-folding row is the newest and the only one found by a fuzzer rather than by hand.** It is a different shape from the rest: not an unhandled node, but a *second implementation* of a handled one. Beside each 32-bit gadget (`<`, `/`, `%`, `&`, `<<`, ...) sat a constant-folding fast path, and none of the five performed the range check that `emit_num2bits` makes the gadget's whole meaning. So the same program meant two things depending on whether the compiler could see the values — and the folded meaning was a 254-bit canonical `Fr` ordering, which answers `0 - 1 >= 0` as **true**. The generalisation is the same as the `optimize_circuit` row's: *enumerate every implementation of a rule, not just the one you are editing*. `require_gadget_range` is now called from all five, and a compile-time-known violation is an error rather than an unsatisfiable circuit — the same fail-closed answer, delivered where it costs a line number instead of a debugging session.

The two `ptx_emitter` rows are the ones to read if you only read two. Neither is caught by anything upstream *or* downstream: the emitted PTX is well-formed, `ptxas` accepts it, the kernel launches, and the answer is wrong. The gate that catches them is `tests/ptx_integer_datapath.rs`, which runs 16 operations over 4096 full-range `u32` pairs on the real device and compares against plain Rust — and which was itself verified by mutation, because a differential test whose two sides are both 32 bits wide cannot see a conversion that has silently become an identity. That gap was real: making `emit_convert` return its input unchanged passed the whole file until four width-crossing cases were added.

The `optimize_circuit` row is a different shape from the rest and is here on purpose: it is not an unhandled *case* but an unhandled *consumer*. A pass that rewrites wire ids has two outputs — the constraints and the witness recipes — and updating one of them is the same failure as handling one arm of a match. The lesson generalises to "enumerate everything downstream that holds the thing you are renaming", and the fix uses the same device as the rule below: an exhaustive match with no `_ =>` arm, so the next variant cannot be forgotten silently.

**`compact_wires` is the second pass in this emitter that renumbers, and the list of consumers is longer than two**: the constraints, the witness recipes (**keys as well as the linear combinations inside them**), the variable-name table, the three boundary lists, `unconstrained_hint_vars`, and `next_var_id`. Miss any one and the circuit still compiles. The list is written out in that function's doc comment rather than left to be rediscovered, and each entry has a mutation in `tests/zk_wire_compaction.rs` that fails when it is dropped. If you add state to `ZkEmitter` that is indexed by wire id, it belongs in both.

The three before it are worth reading as a set, because none of them is a `_ =>` arm in a *verifier*. Two are in the backend and one is in an interval domain, and they show the rule is not really about SMT encodings: **anywhere a pass answers a question with "nothing", the caller reads that as "fine".** An emitter that emits nothing for an unhandled call, and a tracker whose state does not change on entering a branch, are the same mistake as `_ => "0"` — they differ only in which layer discards the obligation.

The correct options for an unhandled node are, in order of preference:

1. **Model it soundly** — over-approximate in the direction that makes the obligation *harder*. `Stmt::If` is now handled by havoc: every variable a branch might assign gets a fresh unconstrained value, so the invariant must hold for anything the branch could have produced. Nested loops likewise.
2. **Refuse with a reason** — `smt_unmodellable` names the construct and rejects. `Y_ALLOW_UNVERIFIED_INVARIANTS=1` is the loud escape hatch.
3. **Never** skip it, substitute a neighbouring operator, or fold it to a constant.

A whitelist is acceptable only when the reason it is safe is *written down and checkable*. `Stmt::Expr` is allowed because Y has no way for a callee to write a caller's local integer without being handed a reference, and the tracked variables are all integer scalars — so `takes_reference` rejects the one case that would break the argument. That is a stated assumption, not a silent one.

## Security, Safety & Verification Constraints

- **Strict `@safe` Block Enforcement**:
  - Code inside `@safe { ... }` blocks requires full variable initialization, forbids raw pointer dereferences, and mandates `@invariant(...)` on all loops. Never disable or bypass `@safe` checks in `type_checker.rs`. All three are real and tested: probes for each are rejected with `[Strict Safety] ...`.
  - **`@invariant` is discharged by Z3, and an invariant that CANNOT be checked now fails the build.** This is a deliberate reversal. The four `run_z3` call sites used to print `[Warning] SMT Solver execution failed` to stdout and continue, so on any machine without z3 - the default - every invariant was accepted unchecked: `@invariant(i > 1000)` on a `0..10` loop compiled cleanly and printed "Compilation Successful!". `smt_unavailable` now pushes an error instead; `Y_ALLOW_UNVERIFIED_INVARIANTS=1` restores the old behaviour loudly for anyone who truly cannot install a solver. **Do not "fix" a CI failure by setting that variable** - it means the safety property is not being checked at all.
  - **The solver search covers `Y_Z3_PATH`, `PATH`, `venv/bin/z3`, `.venv/bin/z3`, `z3/build/z3`, `$HOME/.local/bin/z3`** (`z3_candidates`). It used to be three entries, and this repo has a working `venv/bin/z3` that the old list missed - so the compiler reported the solver as missing on a machine that had one. `pip install z3-solver` into the repo venv is enough.
  - **The SMT encoding itself was unsound until now, and the fix is the design rule above.** `trace_body_statements` ended in `_ => {}`, so a statement it did not model was skipped - and dropping a body's effects makes the preservation obligation strictly EASIER. The identical violation was rejected when written plainly (`i = i - 100;`) and ACCEPTED when wrapped in a trivially-true `if`. `expr_to_smt` was the same shape: `_ => "0"` for any unrecognised expression (a call, an index, a float literal), `_ => "+"` for unrecognised binary operators (so `x & y` was proven as `x + y`), `_ => opnd` for unary ones (so `*p` was proven as `p`). Both are fallible now; branches and nested loops are havoc'd rather than skipped. Guarded by `nested_if_cannot_hide_a_false_invariant`, `unencodable_operator_is_refused_not_mistranslated` and `ordinary_loop_bodies_still_verify` - the last one matters as much as the others, because rejecting everything unmodelled is sound and useless.
  - The verification itself is sound in both directions, confirmed with a solver present: `@invariant(i > 1000)` over `0..10` is rejected (`Z3 returned: sat`), `@invariant(i >= 0)` is accepted. Guarded by `tests/safe_invariant_enforcement.rs`, which drives the real binary as a subprocess because the behaviour depends on the environment and mutating `std::env` from a test races the rest of the suite. **That file's third test is the only thing proving the SMT layer does anything at all** - it skips when no z3 is found, so CI without z3 is not testing `@safe`'s central claim.
- **High-Risk `chisel` Blocks**:
  - `chisel { ... }` blocks allow inline register and direct memory-bus access. Treat changes to `chisel` parsing or emission as high-risk; require explicit verification before modifying low-level hardware access logic.
- **Numerical Drift & Bound Guarantees**:
  - `@ZeroDrift` accumulates in an exact integer/fixed-point representation chosen per device, and `@bounds(min, max)` enforces static index bounds. Ensure type checker interval bounds evaluations remain sound.
  - **It used to do literally nothing** - lexed, parsed, counted, printed as an advisory, read by no backend, so the output was byte-identical with and without it. It is real now: `src/zero_drift.rs` selects the representation, `llvm_emitter.rs` lowers it (4 sites: alloca type override in `emit_alloca_for_block`, init conversion in `Stmt::Let`, scaled `add` in `Stmt::CompoundAssign`, `sitofp`+`fdiv` on the `Expr::Ident` read, plus `infer_type` reporting `double` because the accumulator is STORED as an integer but READS as a float).
  - **Only integer/fixed-point is drift-free; `f64` is not.** Floating-point addition is non-associative, so a reduction's result depends on the order the hardware combined it in - more mantissa drifts less and still drifts. The old profile's `DRIFT_FREE_TYPES=Q32.32,F64` conflated exact with precise. `DriftRepr::is_exact` keeps them apart and a float is **never** selected however fast it measures.
  - **The choice is measured, not assumed.** `measure_accumulate_costs` JITs a serially dependent accumulate chain per candidate. On an RTX 4070 Ti SUPER: Q16.16 ~1790, Q32.32 ~1922, I64 ~2106, F64 ~17726 ps/acc - so exact fixed-point is ~9x cheaper than the "just use higher precision" answer, and the GeForce FP64 penalty shows up exactly where it should. Cached per GPU in `.ysu_hw_profile` as `DRIFT_ACC_<repr>_<gpu>`.
  - **The probe is easy to break and self-checks.** `Q32.32` and `Int64` emit byte-identical PTX, so any gap between them is measurement error - they read 766x apart, then 48x apart, before settling within a few percent. Both early versions were timing a chain ptxas had deleted: first because `acc += step` with a loop-invariant step folds to `acc + N*step`, then because a chain seeded from a **literal** is a compile-time constant however tangled it is. The probe now feeds two registers into each other AND loads its seed from device memory. `q32_32_and_int64_probes_are_identical` and `probe_is_not_constant_foldable` guard both properties - do not "simplify" either away.
  - **A bare `F32` accumulator is correctly rejected**: nothing exact holds 3.4e38 at 2^-24. `@bounds(min, max)` states the real range and makes it satisfiable, which is the intended usage. Only `+=` and `-=` are accepted; `*=` would reintroduce rounding into the accumulation.
  - `tests/zero_drift_end_to_end.rs` compiles a program with `clang` and **runs it**, summing the same 4001 terms in opposite orders and asserting the results are bit-identical - with a control asserting that sequence genuinely drifts in `f32`, so the result cannot be vacuous. It links a two-line shim rather than `c_src/runtime.c`, which currently fails to compile for an unrelated reason (static-after-non-static declaration in `shadowplay_gui.h`).
- **Linear Resource Tracking**:
  - Async memory tokens must be tracked via `linear_tracker.rs` to guarantee single-consumption semantics.
  - **"Exactly once" is a claim about executions, and the tracker was checking source lines.** It set a `consumed` flag the first time the walk passed a `pipe.wait(t)` without asking whether that statement runs, or how often, so two programs compiled clean: `if n { pipe.wait(t); }` (awaited on one path out of two - the exact missing-await race the mechanism exists to prevent) and `for i in 0..4 { pipe.wait(t); }` (one copy, four awaits - the double-consume it *does* reject when the waits are written consecutively). `LinearTracker` now records the conditional and loop nesting depth at creation and compares it against the depth at consumption; `type_checker` drives this with `enter_conditional`/`enter_loop` around `Stmt::If`, `Stmt::For` and `Stmt::While` bodies. A `while` body enters **both**, because it may also run zero times.
  - **The positive cases matter as much as the negative ones.** Rejecting every `pipe.wait` under a loop is sound and would ban the copy-and-await-per-iteration shape that every real pipelined kernel is built from. The rule is depth *relative to creation*, so same-depth pairs still compile. `tests/linear_tracker_enforcement.rs` is 10 tests, 6 negative and 4 positive, driven through the real binary because an earlier instance of this bug was entirely in the wiring rather than in the tracker.
  - This module had **zero tests** before that file. Its guarantee had never been checked, in either direction - which is also why nobody noticed that the backend was discarding it (see gotcha #8 on `pipe.wait`).
