# RT Core + Tensor Core Fused Attention: Investigation Findings (Scaffolding, Not a Capability)

This is an investigation doc, not a benchmark results doc. This session's brief flagged the RT+Tensor Core dual-accelerator story as the pitch's centerpiece claim and asked it to be checked first, before investing in anything else. It was checked first. The verdict: **`coprocessor_scheduler.rs`, `ir_grapher.rs`, and `rt_core_emitter.rs` are a real, tested *simulation* of what a dual-accelerator scheduler would look like - a graph builder, a cost model, and PTX-text emission that name-checks the right instructions in comments - but the RT Core side has never computed anything, cannot compute anything as currently designed, and the compiled Tensor Core side has been proven, on real hardware, to be dead code.** This is not "unvalidated" or "needs more testing" - it is a stronger, more specific finding: the machinery does not and structurally cannot do what the pitch would need it to do. Recommend dropping this as a pitch claim, or reframing it explicitly as "scheduling simulation for future hardware-software co-design," not "Y already fuses RT and Tensor Core work."

## What's real

- `ir_grapher.rs`'s AST-to-graph lowering (`DependencyGrapher`), pipeline classification, and the `OperatorFusionPass` graph-rewrite are real, working Rust code with real unit tests (`test_operator_fusion_pass`) - they correctly build a dependency graph and correctly merge label-matched nodes.
- `coprocessor_scheduler.rs`'s slot assignment and "overlap savings" arithmetic is real, working Rust code that does what it claims *as a scheduling simulation*: given a graph and hardcoded per-op-type cycle-cost constants (see below), it computes a plausible-looking parallel-vs-sequential cycle estimate.
- The type checker's `@safe`/`Fragment`/linear-obligation checks on `tests/coprocessor_attention.ysu` pass, and the Y CLI's lexer/parser/`--emit-coprocessor` pipeline runs end-to-end without error.

## What's not real

1. **The "cycle cost" numbers driving every scheduling decision are hardcoded guesses, not measurements.** `ir_grapher.rs::estimate_expr_cycles` returns fixed constants per call name (`"rt_nearest_neighbor" => 180.0`, `"mma_sync" => 42.0`, `"ldmatrix" => 28.0`, etc.) - not derived from `sentinel.rs`'s real hardware-probed `HardwareProfile` (which is threaded through `schedule()` but only used for `bar_sync_latency_cycles`/`hmma_f16_latency_cycles`, never for the per-node costs that actually drive the "overlap savings" number). The "Overlap Savings: 133 cycles" printed by `--emit-coprocessor` is arithmetic on invented numbers, not a measurement of anything.
2. **`rt_core_emitter.rs` never invokes real RT Core hardware, and structurally cannot.** There is no public PTX ISA instruction for BVH/ray-tracing hardware - real RT Core access requires the OptiX host API (an acceleration structure built on the host, a pipeline, a shader binding table) compiled through OptiX's own NVVM-based device compiler, which a monolithic hand-written-PTX-text emitter cannot replicate by construction. Concretely, `emit_nearest_neighbor` (the function `tests/coprocessor_attention.ysu`'s `rt_nearest_neighbor(128, 8)` call lowers to) never reads the dataset it's supposedly searching (the `rt_A_ptr` parameter is loaded but never referenced in the emitted body) and its "k-nearest-neighbor" loop unconditionally writes the constant `FLT_MAX` (`0f7F7FFFFF`) into all 8 output shared-memory slots - it is not an approximation of a real search, it is a loop that writes one constant 8 times. `emit_gemm_ray_plane`'s "RT hardware returns: t_hit" comment is followed by `mov.f32 result, tmin;` - moving the literal constant 0.0 into the "result" register, not reading anything from any hardware unit.
3. **Confirmed on real hardware, not just by reading the code**: `target/release/Y tests/coprocessor_attention.ysu --emit-coprocessor`'s own output is not valid, assemblable PTX by itself (`ptxas` rejects it: undeclared registers, and separately a `.version`/`.target` mismatch) - it requires a hand-written Python wrapper (`tests/benchmark_coprocessor_physical.py`'s `wrap_ptx`) that string-patches in register declarations "matching Y compiler register allocations" (a human's guess, not something the compiler itself guarantees). Once wrapped and loaded via `cp.RawModule` (which does succeed), disassembling the real compiled SASS (`ptxas -O3` + `cuobjdump --dump-sass`) shows the entire kernel compiles down to 9 instructions: write the constant `FLT_MAX` to shared memory twice, run a small FP16-packing loop over it, and exit. **Zero RT Core instructions, zero `HMMA`/tensor-core instructions, zero global memory traffic anywhere in the compiled binary.** All 5 of the `.ysu` file's `ldmatrix`+`mma.sync` PTX text sequences were proven dead code by `ptxas`'s own optimizer, because the kernel's parameter list has no output pointer at all - nothing the kernel computes can leave the kernel, so the real compiler correctly deleted all of it.
4. **The benchmark script this machinery is checked against compares two pieces of filler code against each other.** `benchmark_coprocessor_physical.py`'s `NAIVE_CUDA_CODE` "RT Traversal Latency Simulation" is, by its own comment, "Simulate RT Core O(log N) tree search latency (approx 200 cycles of dependent loops)" - a busy-loop tuned to *cost about as much as the RT trace was estimated to cost*, not a real search either. Both the warmup and timed loops wrap every kernel launch in a bare `except: pass`, so even a hard crash would silently report a timing number. This script did not run to completion this session (an unrelated, pre-existing NVRTC include-path issue in this environment breaks the *naive CUDA* comparator's compilation, matching a known gotcha this project's own commit history already flags) - but even a working run would not have been evidence of anything, per points 2-3 above.

## Bottom line for the pitch

Do not present the coprocessor scheduler's "N cycles saved by overlapping RT+Tensor" output, or any number from `benchmark_coprocessor_*.py`, as evidence of anything - it is not measuring RT Core or Tensor Core work, on this or any hardware, as currently built. If a dual-accelerator story is wanted for this pitch, it needs to be reframed around what's actually true (a real, if synthetic, dependency-graph scheduler and cost-model design) or dropped in favor of the fusion results that *are* real this session (`benchmark_y_bias_relu_gemm_results.md`, `benchmark_y_rmsnorm_rope_results.md`).
